# 프록시 / 리버스 프록시

[SSE](../spring/sse.md) 노트에 "중간의 프록시나 서블릿 컨테이너가 끊는다", [WebSocket](../spring/websocket.md) 노트에 "프로토콜이 바뀌니까 프록시 설정도 손봐야 한다"고 적어놓고 정작 프록시를 안 봤다. 그걸 봤다.

방향을 계속 반대로 알고 있었다.

## 둘 다 중간에 선 대리인이다

프록시(proxy)는 "대리"다. 내가 직접 안 하고 중간에 누가 대신 해주는 것.

포워드든 리버스든 **위치는 똑같이 중간**이다. 차이는 하나뿐이다. **누구를 대신하느냐.**

```
포워드 프록시 (그냥 "프록시")

  클라이언트 ──▶ [프록시] ──▶ 서버
   └───── 이쪽 편 ─────┘

  "내가 직접 안 가고 쟤가 대신 다녀와줘"
  서버는 프록시만 보인다. 진짜 클라이언트를 모른다.
```

```
리버스 프록시

  클라이언트 ──▶ [프록시] ──▶ 서버
                  └──── 이쪽 편 ────┘

  "손님은 나한테 오세요. 뒤에 누가 있는지는 몰라도 됩니다"
  클라이언트는 프록시만 보인다. 진짜 서버를 모른다.
```

**가려주는 쪽이 반대다.**

| | 누구 편 | 누가 가려지나 | 모르는 쪽 |
|---|---|---|---|
| 포워드 프록시 | 클라이언트 | 클라이언트 | 서버 |
| 리버스 프록시 | 서버 | 서버 | 클라이언트 |

`reverse`(역방향)라는 이름이 **가려주는 방향이 뒤집혔다**는 뜻이다. 위치가 뒤라는 게 아니다. 이걸 "뒤에 있는 프록시"로 읽어서 한참 헷갈렸다.

익숙한 예로 붙이면 이렇다.

```
포워드   회사에서 외부 사이트 나갈 때 거치는 사내 프록시
         VPN 도 비슷한 자리 (내 출발지를 가린다)

리버스   톰캣 앞에 선 nginx / Apache
         서버가 여러 대여도 밖에서는 주소 하나로 보인다
```

## 왜 쓰냐 — 흩어진 일을 한 곳으로 모은다

한 줄로 말하면 **양쪽을 안 고치고 중간에 일을 끼워넣을 수 있어서**다. 클라이언트도 서버도 그대로 두고 그 사이에서 처리한다.

리버스 프록시 쪽이 개발하면서 훨씬 자주 만난다.

- **주소를 하나로 모은다** — 뒤에 톰캣이 3대여도 밖에서는 도메인 하나다. 서버를 늘리거나 한 대를 내려도 클라이언트는 모른다. 로드밸런싱·무중단 배포가 여기서 나온다.
- **TLS를 한 곳에서 끝낸다** — 인증서를 프록시에만 넣고 뒤는 평문 HTTP로 보낸다. 톰캣 3대에 각각 인증서를 넣고 갱신할 필요가 없다.
- **뒤를 숨긴다** — 톰캣 포트(8080)나 버전이 밖으로 안 드러난다. 직접 노출하면 그 정보가 공격의 출발점이 된다.
- **공통 처리를 한 곳에서** — 정적 파일 응답, 압축, 캐시, 접근 제한, 로깅. 애플리케이션 코드를 안 건드리고 붙인다.

포워드 프록시는 반대쪽 이유다.

- **나가는 트래픽을 통제한다** — "이 사이트는 막고 이건 허용"을 한 곳에서 걸고, 누가 어디에 접속했는지 기록한다.
- **내 출발지를 가린다** — 서버 입장에서는 프록시의 IP만 보인다.

### 패턴은 하나다

```
각 서버에 인증서 3개   →  프록시에 1개
각 서버에 접근 제한    →  프록시에 1곳
각 클라이언트에 설정   →  프록시에 1곳
```

**중간에 있으니 모든 트래픽이 거기를 지나가고, 그래서 거기서 한 번만 하면 된다.** 그게 프록시의 존재 이유다.

## 톰캣을 늘리는 것과 기능을 추가하는 것은 다르다

"주소를 하나로 모은다"를 듣고 **톰캣을 하나 더 띄우면 `example.com/new` 로 바로 들어가는 줄 알았다.** 아니다.

리버스 프록시는 **"어떤 경로는 어디로 보낸다"는 표**를 보고 넘긴다. 그 표에 없으면 404다.

```nginx
location /order/ { proxy_pass http://127.0.0.1:8081/; }   # 주문 톰캣
location /user/  { proxy_pass http://127.0.0.1:8082/; }   # 사용자 톰캣

# /new/ 를 쓰려면 이 줄을 추가해야 한다
location /new/   { proxy_pass http://127.0.0.1:8083/; }
```

추가하고 설정을 reload 해야 적용된다. **톰캣만 띄우면 프록시는 그런 게 생겼는지 모른다.**

### 숨겨지는 것과 안 숨겨지는 것

내가 섞어서 생각한 게 이 둘이었다.

```
① 같은 기능을 늘린다 (스케일 아웃)
   주문 톰캣 1대 → 3대
   → upstream 목록에 한 줄 추가. 경로 규칙은 그대로
   → /order 그대로 동작

② 새 기능을 추가한다
   → 새 location 블록이 필요
   → 안 적으면 /new 는 404
```

| | 프록시 설정 | 클라이언트가 아나 |
|---|---|---|
| ① 같은 기능 증설 | upstream 한 줄 | 모른다 |
| ② 새 기능 추가 | location 블록 추가 | 새 경로를 알아야 한다 |

**①은 숨겨지고 ②는 숨겨지지 않는다.** 새 기능은 새 주소니까.

### 한 곳에 모은 대가

"흩어진 일을 한 곳으로 모은다"가 양면이다.

```
좋은 면   설정이 한 곳에 있다
나쁜 면   새 기능마다 그 한 곳을 고쳐야 한다
          그 한 곳이 죽으면 전부 죽는다
```

규모가 커지면 이 수작업이 부담이 돼서, 톰캣이 뜰 때 **스스로 등록**하는 방식(서비스 디스커버리)을 쓴다. 쿠버네티스나 Consul이 그걸 해준다. 그러면 "띄우면 들어가진다"에 가까워진다.

다만 그건 **프록시가 똑똑해진 게 아니라 등록을 자동화한 것**이다. 표를 보고 넘기는 건 똑같다.

## 무중단 패치는 프록시만으로 안 된다

프록시를 넣으면 무중단 패치가 되는 줄 알았다. **필요조건이지 충분조건이 아니다.**

> 프록시는 트래픽을 돌릴 수 있게 해주지만, **상태를 옮겨주지는 못한다.**

```
톰캣A 내리고 톰캣B로 돌린다
  → 요청은 B로 잘 간다               ✅ 프록시가 해준다
  → A 메모리에 있던 것은?            ❌ 사라진다
```

### 세션이 먼저 걸린다

로그인 세션이 톰캣 메모리에 있다. A를 내리면 **A에 붙어 있던 사용자는 로그아웃된다.**

```
① 세션을 밖으로 빼낸다        Redis 등에 저장 → 어느 톰캣이든 읽는다
② 같은 사용자는 같은 톰캣으로  sticky session → 그 톰캣 내리면 똑같이 끊김
```

①이 제대로 된 방법이고 ②는 증상을 미루는 쪽이다.

### 그리고 내 SSE 코드가 걸린다

이게 제일 중요한 발견이었다. [SSE](../spring/sse.md) 노트에 쓴 그 Map이다.

```java
private static final Map<String, EmitterWrapper> EMITTERS = new ConcurrentHashMap<>();
```

`static` 이다. 즉 **그 톰캣 JVM 안에만 있다.** 톰캣이 2대가 되면 이렇게 된다.

```
톰캣A   EMITTERS: [사용자1, 사용자2]
톰캣B   EMITTERS: [사용자3, 사용자4]

수집기 데이터가 톰캣A 로 들어옴 → broadcast
  → 사용자1, 2 만 받는다
  → 사용자3, 4 는 화면이 안 바뀐다
```

**`broadcast` 가 전체 broadcast 가 아니라 "내 톰캣에 붙은 사람들"이 된다.** 에러도 안 난다. 그냥 절반이 갱신을 못 받는다.

ES 롤업 노트에서 "게이트에 막혀 못 받는 상황"을 걱정했는데, 톰캣을 늘리면 그것과 같은 증상이 구조적으로 생긴다. 지금은 톰캣 한 대라 안 보이는 문제다.

| | 프록시가 해주나 |
|---|---|
| 트래픽을 다른 톰캣으로 돌리기 | ✅ |
| 세션 유지 | ❌ 앱이 해야 함 |
| SSE · WebSocket 연결 공유 | ❌ 앱이 해야 함 |

**프록시를 넣는 건 무중단의 시작이고, 나머지는 "메모리에 뭘 들고 있나"를 정리하는 일이다.**

## 리버스 프록시는 막는 게 아니라 받는 것이다

"리버스 프록시로 외부 나가는 걸 막는 거냐"고 생각했는데 **방향이 반대**였다.

```
포워드 프록시   나가는 걸 통제한다      (클라이언트 편)
리버스 프록시   들어오는 걸 받는다      (서버 편)
```

리버스 프록시는 **내 서버 앞에 세우는 것**이다. 내가 서버 운영자일 때 쓴다. 직원이 어디 접속하는지 막는 건 포워드 프록시다.

회사에서 특정 사이트를 막는 건 포워드 프록시가 맞다. **회사가 세운 장비고 사내 트래픽이 거기를 경유**하니까.

## 국가 사이트 차단은 프록시가 아니다

한국에서 차단된 사이트가 안 들어가지는 것도 프록시인가 했는데 아니다. 핵심 차이가 이거다.

```
프록시      내 트래픽이 그리로 "간다"              (경유)
ISP 차단    내 트래픽이 지나가는 길목에서 "본다"    (감시)
```

프록시는 목적지가 프록시다. ISP 차단은 목적지가 그대로인데 중간 회선에서 들여다본다. **경유하는 게 아니라서 프록시가 아니다.**

방식이 두 단계로 발전했다.

### DNS 차단

[DNS](dns.md) 노트에 "공유기가 DNS 서버이기도 하다"고 적었는데, 그 질의가 결국 ISP DNS로 간다. 차단 목록에 있는 도메인을 물어보면 **진짜 IP 대신 경고 페이지 IP**를 돌려준다.

```
"blocked.com 주소 뭐야?"  →  ISP DNS  →  경고 페이지 IP
```

### SNI 차단

HTTP 시절에는 요청의 `Host` 헤더가 평문이라 그걸 보고 막았다. HTTPS가 되면서 내용이 암호화돼 못 보게 됐다.

그런데 **TLS 핸드셰이크의 SNI(Server Name Indication)는 평문이다.**

```
TLS 핸드셰이크 첫 패킷
  ├─ SNI: "example.com"      ← 평문. 암호화 전에 나간다
  └─ 이후 내용               ← 암호화됨
```

SNI가 왜 평문이냐면 — **서버가 어느 인증서를 줘야 할지 결정하려면 먼저 이름을 알아야** 한다. IP 하나에 사이트 여러 개가 올라가 있을 때 "너 누구 찾아왔니"를 암호화 전에 말해줘야 한다. 순서상 암호화할 수가 없다.

그래서 그 평문 필드를 보고 차단한다.

[HTTPS](https.md) 노트에 아직 SNI를 안 적었다. TLS 핸드셰이크 정리할 때 같이 넣어야 한다.

### 세 개가 다 다른 자리다

| | 누가 | 방식 |
|---|---|---|
| 회사 사이트 차단 | 회사 | 포워드 프록시 (경유) |
| 국가 사이트 차단 | ISP | DNS 응답 조작 + SNI 검사 (감시) |
| 리버스 프록시 | 서버 운영자 | 들어오는 요청 받기 |

**리버스 프록시는 이 중 차단과 가장 거리가 멀다.**

## 포워드 프록시는 어디에 설정하나

공유기인가 했는데 아니다. 보통 **별도 장비나 서버**다.

```
사내 서버 한 대에 프록시 소프트웨어   Squid 등
방화벽 · UTM 장비의 프록시 기능       장비에 내장
클라우드 서비스                       트래픽을 외부 서비스로 보냄
```

그런데 더 중요한 질문이 남는다.

> **PC가 "프록시를 거쳐 가야 한다"는 걸 어떻게 아나?**

프록시를 세워놓기만 하면 아무 일도 안 일어난다. PC가 안 쓰면 그냥 직접 나가버린다.

### 거치게 만드는 방법 세 가지

**① PC에 직접 설정** — 윈도 네트워크 설정이나 브라우저에 프록시 주소를 적는다. 문제는 **사용자가 끌 수 있다**는 거다. 그래서 회사에서는 그룹 정책으로 잠가 못 바꾸게 한다.

**② PAC 파일** — "이런 주소는 프록시로, 저런 건 직접"을 적은 스크립트를 PC가 자동으로 받아 간다. 사내망은 직접, 외부는 프록시로 가르는 식이다.

**③ 투명 프록시** — 여기서 공유기·방화벽이 등장한다. PC는 아무 설정이 없는데 **네트워크 장비가 나가는 트래픽을 강제로 프록시로 돌린다.**

```
PC: "naver.com 으로 직접 갈게"
     ↓
라우터/방화벽: (몰래 프록시로 돌림)
     ↓
프록시: 차단 목록 확인 → 거부
```

PC는 프록시를 거친 줄도 모른다. 그래서 "투명(transparent)"이다. 공유기의 역할이 여기다 — **프록시를 돌리는 게 아니라 프록시로 돌려주는 역할**이다.

### 강제의 핵심은 따로 있다

①·②는 전부 "PC가 협조해준다"는 전제다. 우회가 가능하다. 그래서 실무에서 하는 건 이거다.

```
방화벽: 프록시 서버 외에는 외부로 나가는 걸 전부 막는다
```

프록시를 안 거치면 **아예 통신이 안 된다.** 선택이 아니라 유일한 출구가 된다. 설정을 끄면 인터넷이 안 되니 끄는 의미가 없다.

**프록시 설정은 "거치게 해달라는 안내"고, 방화벽이 "안 거치면 못 나간다"를 만든다.** 둘을 같이 써야 통제가 된다.

## 방화벽만으로는 도메인을 못 막는다

"그럼 방화벽에 설정하면 되겠네" 했는데 역할이 다르다. [IP/서브넷/포트](ip-subnet-port.md) 노트에 내가 쓴 게 답이었다.

> **방화벽 정책 = IP 대역 + 포트**

여기에 **이름이 없다.** 전통적인 방화벽은 `naver.com` 이라는 글자를 모른다. IP와 포트만 본다.

IP로 막으려면 두 가지가 걸린다.

- **IP가 여러 개고 계속 바뀐다.** 큰 서비스는 부하 분산·CDN 때문에 IP가 수십 개이고 수시로 변한다. 오늘 적어둔 IP가 내일 다르다.
- **IP를 공유한다.** CDN은 IP 하나에 여러 고객사 서비스가 얹혀 있다. 그 IP를 막으면 **엉뚱한 서비스까지 같이 막힌다.** 과차단이다.

그래서 이름으로 막아야 하고, 이름을 보려면 더 위 계층을 봐야 한다.

```
L3/L4 방화벽    IP · 포트        →  "10.0.0.5:443 막아"      이름 모름
L7 (프록시)     SNI · Host 이름  →  "naver.com 막아"         이름 봄
```

### 그래도 실무에서는 맞는 말이다

요즘 장비는 **둘을 겸한다.** 차세대 방화벽(NGFW)이나 UTM이 L7까지 들여다본다.

```
옛날   방화벽(IP·포트)  +  프록시(이름)      장비 두 개
지금   NGFW / UTM 한 대가 둘 다               장비 한 개
```

"방화벽에 설정한다"가 실무적으로는 맞다. 다만 그때 그 장비는 **방화벽 기능이 아니라 L7 기능으로 막고 있는 것**이다.

| | 보는 것 | 도메인 차단 |
|---|---|---|
| L3/L4 방화벽 | IP · 포트 | ❌ 이름을 모른다 |
| 포워드 프록시 | SNI · Host | ✅ |
| NGFW / UTM | 둘 다 | ✅ (L7 기능으로) |

역할 분담은 이렇다.

```
L7 로 이름 보고 차단        ← 어디로 가려는지 판단
방화벽으로 우회 경로 차단    ← 프록시 안 거치면 못 나가게
```

**"무엇을 막을지"는 이름을 보는 쪽이, "다른 길로 못 가게"는 IP·포트를 보는 쪽이 한다.**

---

프록시를 공부하면서 제일 많이 틀린 게 방향이었다. `reverse` 를 "뒤에 있다"로 읽어서 리버스 프록시가 나가는 걸 막는 거라고 생각했다. **가려주는 쪽이 뒤집혔다는 뜻**이고, 둘 다 위치는 중간이다.

그리고 프록시가 해주는 일의 범위를 과대평가했다. 주소를 하나로 모아주니 톰캣을 띄우면 알아서 붙고 무중단 배포도 될 것 같았는데, 프록시는 **표를 보고 트래픽을 넘기는 것까지**다. 새 경로는 내가 적어야 하고, 메모리에 들고 있는 상태는 내가 밖으로 빼야 한다.

그 "메모리에 들고 있는 상태"가 내 SSE 코드의 `static EMITTERS` 였다. 지금은 톰캣이 한 대라 안 보이지만, 두 대가 되는 순간 broadcast 가 절반에만 간다. 프록시를 공부하고 나서 내 코드의 제약을 알게 된 게 제일 소득이었다.
