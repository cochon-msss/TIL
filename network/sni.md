# SNI (Server Name Indication)

[프록시](proxy.md) 노트를 쓰면서 SNI를 한 단락만 적었는데, 파고 보니 분량이 됐다. 따로 뺐다.

한 줄로 말하면 **TLS 핸드셰이크 맨 앞에 "나 이 사이트 찾아왔어"를 평문으로 적는 칸**이다.

## IP 하나에 사이트 여러 개

서버 한 대에 사이트를 여러 개 올리는 건 흔하다. IP는 하나인데 도메인은 여러 개다.

```
IP 1.2.3.4  ──┬── a.com
              ├── b.com
              └── c.com
```

요청이 들어왔을 때 **누구를 찾아온 건지** 알아야 한다. IP만으로는 구분이 안 된다.

HTTP는 간단히 해결했다. 요청에 적어서 보낸다.

```
GET / HTTP/1.1
Host: b.com        ← 이거 보고 판단
```

[HTTP](http.md) 노트의 요청 메시지에 `Host` 가 있는 이유가 이거다. 그냥 참고용이 아니라 **없으면 어느 사이트인지 모른다.**

## HTTPS는 순서가 꼬인다

HTTPS는 **암호화를 먼저 시작**한다. 그런데 암호화를 시작하려면 서버가 **인증서를 보내줘야** 한다.

문제는 인증서가 도메인마다 다르다는 거다. `a.com` 인증서를 `b.com` 접속에 쓰면 브라우저가 경고를 띄운다.

```
암호화를 시작하려면    → 인증서를 골라야 한다
인증서를 고르려면      → 어느 사이트인지 알아야 한다
어느 사이트인지는      → Host 헤더에 있다
Host 헤더는           → 암호화된 다음에 온다
```

**순환이다.**

[DHCP](dhcp.md) 때 본 그 모양이다.

```
DHCP:  게이트웨이를 쓰려면 → 게이트웨이 주소를 알아야 → 그걸 알려주는 게 DHCP
SNI :  암호화하려면       → 인증서를 골라야       → 이름이 암호화 안에 있다
```

둘 다 **자기가 만들어낼 값이 자기한테 필요한** 구조다. 그러면 그 단계가 시작조차 못 한다.

## 그래서 암호화 전에 평문으로 말한다

해법도 DHCP와 같은 모양이다. DHCP가 IP 없이 `0.0.0.0` 으로 외쳤던 것처럼, **순서상 암호화할 수 없으니 평문으로 먼저 알려준다.**

```
① 클라이언트 → 서버    "안녕, 나 b.com 찾아왔어"   ← SNI. 평문
② 서버                 b.com 인증서를 고른다
③ 서버 → 클라이언트    b.com 인증서 전달
④ 그 다음부터          암호화 시작
```

①의 그 이름 칸이 SNI다. **암호화를 시작하기 위한 정보라서 암호화할 수 없다.**

## SNI가 없으면 IP 하나에 사이트 하나

| | IP 1개에 도메인 여러 개 | 이름을 어디서 |
|---|---|---|
| HTTP | 처음부터 가능 | `Host` 헤더 |
| HTTPS (SNI 전) | **불가능** | 알 방법이 없었다 |
| HTTPS (SNI 후) | 가능 | SNI |

SNI는 새 기능을 만든 게 아니라 **HTTPS가 HTTP를 따라잡은 것**이다. HTTP에서 당연히 되던 걸 HTTPS에서도 되게 메운 거다.

이게 꽤 큰 문제였다. IPv4 주소는 수가 정해져 있고 비싸다. SNI 없던 시절에는 **HTTPS 사이트 하나당 IP 하나**를 사야 했다.

```
사이트 100개를 HTTPS 로 운영  →  IP 100개 필요
```

공용 호스팅 업체가 고객마다 IP를 사줄 수 없으니 "HTTPS 쓰려면 전용 IP 추가 요금"이었다.

## 이름을 두 번 쓴다

여기가 제일 헷갈렸다. **이름은 DNS 조회가 끝나면 버려지는 게 아니라 요청과 같이 간다.**

```
① DNS 조회      "b.com 주소 뭐야?"        → 1.2.3.4
② TCP 연결      1.2.3.4:443 으로 붙는다
③ SNI          "나 b.com 찾아왔어"        ← 이름을 다시 말한다
④ 서버          그 이름으로 어느 사이트인지 고른다
```

①에서 이름 → IP, ③에서 **다시 이름**이다. 역할이 다르다.

```
IP    어느 서버까지 갈지         (길 찾기)
이름  그 서버 안의 어느 사이트   (도착 후 구분)
```

아파트로 치면 IP가 **건물 주소**고 SNI가 **몇 호**다. 건물 앞까지는 주소로 가지만 거기서 "누구 찾아오셨어요?"에 답해야 한다.

SNI 값을 DNS가 정해주는 게 아니다. **브라우저가 원래 치려던 이름을 그대로** 넣는다. 같은 이름에서 두 갈래로 갈라져 나간다.

```
주소창에 b.com 입력
  ├─ DNS 조회 → IP 를 얻는다           (어디로 갈지)
  └─ SNI 에 그 이름을 그대로 넣는다     (누구 찾아왔는지)
```

### 방향이 비대칭이다

"IP 로 들어가면 그 사이트로 가야 하는 거 아닌가" 싶었는데 **그럴 수가 없다.**

```
도메인 → IP     N : 1    (여러 도메인이 한 IP를 가리킨다)   정해진다
IP → 도메인     1 : N    (한 IP에 도메인이 수백만 개)       못 정한다
```

IP만으로는 "누구 찾아왔는지"를 서버가 알 수 없다. 그래서 이름이 또 필요하다.

## 실제로 확인해봤다

내 GitHub Pages 주소와 GitHub 자체 사이트를 해석해봤다.

```
> Resolve-DnsName cochon-msss.github.io -Type A
185.199.108.153, 185.199.109.153, 185.199.110.153, 185.199.111.153

> Resolve-DnsName pages.github.com -Type A
185.199.108.153, 185.199.109.153, 185.199.110.153, 185.199.111.153
```

**완전히 같은 IP 4개다.** GitHub Pages는 IP 4개로 전 세계 모든 `*.github.io` 사이트를 서비스한다. 수백만 개가 IP 4개에 올라가 있다.

그 다음 둘을 비교해봤다.

```
① https://cochon-msss.github.io/   →  HTTP 404
② https://185.199.108.153/         →  TLS 신뢰 관계 실패
```

**①은 TLS를 통과했다.** 404는 그 다음 단계다 — 사이트는 찾았는데 올려둔 내용이 없다는 뜻(Pages를 안 켰다). 중요한 건 이름을 말했으니 서버가 인증서를 제대로 골라줬다는 것.

**②는 TLS 단계에서 막혔다.** 이름을 안 말했으니 서버가 기본 인증서를 주고, 브라우저는 "내가 요청한 건 `185.199.108.153` 인데 인증서에 그 이름이 없다"며 거부했다.

[DNS](dns.md) 노트에 적어둔 그 현상이 이거였다.

> ## 참고 - IP로 https 접속하면 인증서 경고가 뜬다

**인증서는 이름에 발급되는 것**이라서 IP로 가면 맞출 대상이 없다.

### 와일드카드 인증서

인증서를 찍어보니 `CN=*.github.io` 였다. **와일드카드**다. `*.github.io` 전체를 인증서 하나로 덮는다.

그래서 이 경우는 SNI로 인증서를 **고를** 필요가 없다. 어느 `*.github.io` 로 와도 같은 인증서다.

SNI가 꼭 필요해지는 건 **인증서가 서로 다를 때**다. GitHub Pages에 커스텀 도메인을 붙이면 도메인마다 인증서가 따로 발급되니 같은 IP에서 골라줘야 한다.

```
*.github.io 끼리     와일드카드 1개로 충분. SNI 로 고를 게 없음
커스텀 도메인들      도메인마다 인증서 → SNI 로 골라야 함
```

인증서를 고르는 것과 **사이트 내용을 고르는 것**은 별개다. 와일드카드라도 어느 사용자 사이트를 줄지는 SNI(또는 Host)를 봐야 안다.

## SNI를 읽는 건 443을 듣는 놈이다

누가 SNI를 읽고 분기하냐 — **그 IP에서 443 포트를 듣고 있는 프로세스**다. 그리고 그게 보통 리버스 프록시다.

```
브라우저 ──TLS(SNI: order.example.com)──▶ [nginx]   ← 여기서 SNI 를 읽는다
                                             │       인증서 고르고 TLS 끝냄
                                             ▼
                                          톰캣 (평문 HTTP)
```

세 가지가 같은 지점이다.

```
인증서를 가진 쪽  =  SNI 를 읽는 쪽  =  어디로 보낼지 정하는 쪽
```

당연하다. 인증서를 고르려면 SNI를 읽어야 하고, 인증서를 가진 건 TLS를 끝내는 쪽이니까.

| 구성 | 443을 듣는 놈 = SNI를 읽는 놈 |
|---|---|
| 직접 운영 | nginx / Apache |
| 클라우드 | 로드밸런서 |
| CDN | 엣지 서버 |
| 톰캣 직접 노출 | 톰캣 |

`cochon-msss.github.io` 는 세 번째다. `185.199.108.153` 에서 듣고 있는 엣지 서버가 SNI를 읽고 해당 저장소 내용을 내보낸다.

### 톰캣은 SNI를 모른다

프록시를 앞에 두면 이렇게 된다.

```
nginx    TLS 벗겨냄. SNI 읽음. 인증서 처리
  ↓      평문 HTTP 로 전달
톰캣     SNI 가 뭐였는지 모른다. 암호화됐던 것도 모른다
```

톰캣 입장에서는 평범한 HTTP 요청이 온 거다. 그래서 원래 클라이언트 정보를 알려면 **프록시가 헤더에 적어서 넘겨줘야** 한다.

```
X-Forwarded-For     원래 클라이언트 IP
X-Forwarded-Proto   원래 https 였음
X-Forwarded-Host    원래 요청한 도메인
```

"로그에 클라이언트 IP가 전부 프록시 IP로 찍힌다"는 문제가 여기서 나온다.

## nginx 전용 기능이 아니다

처음엔 SNI를 읽으려면 nginx를 써야 하나 했는데, **SNI는 TLS 표준**이다. TLS를 끝내는 모든 소프트웨어가 읽는다.

```
nginx · Apache · HAProxy · Caddy · IIS · 톰캣   전부 읽는다
```

톰캣에 인증서를 직접 넣고 443으로 띄우면 톰캣이 SNI를 읽는다. nginx 없이도 된다. nginx를 앞에 두는 건 **인증서 한 곳 관리·정적 파일·서버 묶기** 때문이고 SNI를 읽으려고가 아니다.

### 읽는 것과 복호화하는 건 별개다

SNI는 평문이다. 그러니까 **복호화하지 않고도 읽을 수 있다.**

```
① TLS 종료 방식     SNI 읽고 + 복호화해서 내용까지 본다
                    → nginx 리버스 프록시. 인증서 필요

② SNI 만 보는 방식   SNI 읽고 + 암호화된 채로 뒤로 넘긴다
                    → HAProxy TCP 모드 등. 인증서 불필요
```

②는 "누구 찾아왔는지만 보고 해당 서버로 그대로 흘려보내는" 구성이다. 중간 장비가 인증서를 안 가져도 되니 **내용을 못 본다.** 보안상 더 깔끔한 경우가 있다.

그리고 ②의 원리가 프록시 노트에 적은 **ISP의 SNI 차단**과 같다.

```
HAProxy TCP 모드   SNI 보고 → 해당 서버로 넘긴다
ISP 차단           SNI 보고 → 차단 목록이면 끊는다
```

**같은 평문 필드를 보고 한쪽은 라우팅하고 한쪽은 차단한다.** 하는 일만 다르고 읽는 방법은 같다.

평문이라는 성질이 양쪽에 다 쓰이는 셈이다. 가상호스팅을 가능하게 한 그 필드로 차단도 한다.

## 설정 한 블록에 다 들어 있다

프록시와 SNI로 배운 게 nginx 설정 하나에 전부 나온다.

```nginx
upstream tomcat_order {
    server 127.0.0.1:8081;          # 증설하면 여기 한 줄 추가 (클라는 모름)
    server 127.0.0.1:8084;
}

server {
    listen 443 ssl;                            # 443 을 듣는다 → SNI 를 읽는 주체
    server_name order.example.com;             # SNI 로 이 블록이 선택된다
    ssl_certificate     /etc/ssl/order.crt;    # 인증서 보유 = TLS 종료
    ssl_certificate_key /etc/ssl/order.key;

    location /static/ { root /var/www; }       # 정적 파일은 nginx 가 직접 응답

    location / {
        proxy_pass http://tomcat_order;        # 나머지는 톰캣으로 (평문 HTTP)
        proxy_set_header X-Forwarded-For   $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

| 줄 | 하는 일 |
|---|---|
| `listen 443 ssl` | SNI를 읽는 주체가 된다 |
| `server_name` | SNI로 블록 선택 → IP 하나에 도메인 여러 개 |
| `ssl_certificate` | TLS 종료. 인증서를 한 곳에서 관리 |
| `location /static/` | 정적 파일을 대신 응답 |
| `proxy_pass` | 경로별 분기 |
| `X-Forwarded-*` | 톰캣이 모르는 원래 정보를 넘겨줌 |
| `upstream` | 같은 기능 증설 (숨겨짐) |

도메인을 추가하려면 `server` 블록 하나 더, 경로를 추가하려면 `location` 하나 더, 서버를 늘리려면 `upstream` 에 한 줄. **전부 이 파일 하나**다.

프록시 노트에 적은 "흩어진 일을 한 곳으로 모은다"의 실제 모습이고, 동시에 "그 한 곳이 죽으면 전부 죽는다"의 이유다.

## 사설 인증서 경고는 프록시로 안 없어진다

여기서 하나 틀렸다. "nginx에 인증서를 몰아두면 사설 인증서 경고가 없어지겠네" 했는데 아니다.

```
브라우저 ──[사설 인증서]──▶ nginx ──[평문 HTTP]──▶ 톰캣
            ↑ 경고는 여기 그대로        ↑ 인증서가 아예 없으니 문제 없음
```

nginx **뒤쪽**은 평문이라 인증서 문제가 없는 게 맞다. 그런데 **브라우저 ↔ nginx 구간**은 여전히 사설 인증서라 경고가 그대로 뜬다.

얻는 건 경고 지점이 줄어드는 것이다.

```
프록시 없음   서버 3대 각각 사설 인증서  →  경고 3번, 갱신 3번
프록시 있음   nginx 하나만               →  경고 1번, 갱신 1번
```

관리는 편해지는데 **경고 자체는 안 없어진다.**

### 없애려면 믿게 만들어야 한다

경고가 뜨는 이유는 "이 인증서를 발급한 곳을 못 믿겠다"다. 그러니 믿게 만들면 된다.

```
① 인증서를 PC 마다 하나씩 등록     서버 늘면 또. 갱신하면 또
② 사내 CA 를 만들고 루트만 등록     그 CA 가 발급한 건 전부 자동 신뢰
```

②가 제대로 된 방법이다. 루트 인증서 **하나**를 PC의 신뢰된 저장소에 넣으면 그 CA로 발급한 건 서버가 몇 대든 경고가 안 뜬다. 그룹 정책으로 배포하면 수동 작업도 없다.

```
사내 CA 루트 1개 등록
  → gitlab.내부도메인     경고 없음
  → jira.내부도메인       경고 없음
  → 새로 만든 서비스도    경고 없음
```

흔히 쓰는 우회가 **검증을 끄는 것**이다. git 설정에 호스트별로 이렇게 넣는 식이다.

```ini
[http "https://내부서버/"]
	sslVerify = false
```

동작은 하는데 그 호스트에 대해 **중간자 공격 탐지를 포기**하는 거다. 사내망이어도 깔끔한 선택은 아니고, 사내 CA를 등록해두면 이 설정이 필요 없어진다.

## 언제 프록시를 두나

| 상황 | 권장 |
|---|---|
| 톰캣 1대, 도메인 1개 | 톰캣 직접도 OK |
| 톰캣 여러 대 | nginx (인증서·분기 한 곳) |
| 도메인 여러 개 | nginx (SNI 분기) |
| 무중단 배포 필요 | nginx 필수 |
| 정적 파일이 많다 | nginx (톰캣 부담 줄임) |

나중에 늘어날 걸 알면 처음부터 두는 게 낫다. 끼워넣으면 인증서·포트·리다이렉트를 다시 손봐야 한다.

그리고 톰캣을 직접 노출하면 **포트와 버전이 밖으로 드러난다.**

---

SNI는 결국 **순서 문제를 푼 것**이다. 암호화를 시작하려면 인증서가 필요하고, 인증서를 고르려면 이름이 필요한데, 이름은 암호화 안에 있었다. 그래서 이름만 암호화 밖으로 꺼냈다.

그 꺼냈다는 성질이 전부로 이어진다. 평문이라서 IP 하나에 사이트 수백만 개를 올릴 수 있게 됐고, 평문이라서 중간에서 보고 차단할 수도 있게 됐다. 가상호스팅과 SNI 차단이 **같은 한 가지 결정의 양면**이다.

[HTTPS](https.md) 노트에 TLS 핸드셰이크를 정리하면 이 노트와 이어 붙어야 한다. SNI는 그 핸드셰이크의 첫 패킷에 있는 필드다.
