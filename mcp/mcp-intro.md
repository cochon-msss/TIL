# MCP (Model Context Protocol)

AI 쪽에서 "MCP 붙인다"는 말이 자꾸 나오는데 뭔지를 몰라서 정리했다.

## 왜 나왔냐

AI는 자기가 학습한 것만 안다. 내가 쓰는 문서나 사내 자료는 세상에 공개된 적이 없으니 모른다. 그래서 물어봐도 못 답한다.

답하게 하려면 자료를 줘야 하는데, 지금까지는 사람이 직접 복붙했다.

```
MCP 없을 때
  나:  "이거 어떻게 하는 거야?"
  AI:  "모르겠습니다"
  나:  (문서 찾아서 복사) "이거 보고 알려줘: ..."
  AI:  "네, 요약하면..."

MCP 붙였을 때
  나:  "이거 어떻게 하는 거야?"
  AI:  (서버한테) "관련 문서 찾아줘"
  AI:  "문서에 따르면..."
```

복붙을 사람이 하냐, AI가 알아서 가져오냐의 차이다.

## 근데 연결 방식이 제각각이면

AI 앱이 3개(Claude, Cursor, VS Code), 붙일 시스템이 4개(GitHub, Slack, DB, Jira)라고 치면 연동 코드를 **3 × 4 = 12개** 짜야 한다.

```
              GitHub  Slack  DB  Jira
Claude Code  │  ①      ②     ③    ④
Cursor       │  ⑤      ⑥     ⑦    ⑧
VS Code      │  ⑨      ⑩     ⑪    ⑫
```

Cursor가 만든 GitHub 연동을 Claude가 못 쓴다. 규격이 다르니까. 이게 M×N 문제다.

MCP를 쓰면 **3 + 4 = 7개**가 된다. 각 앱은 MCP 클라이언트를 한 번만 만들고, 각 시스템은 MCP 서버를 한 번만 만들면 조합이 자동으로 다 연결된다.

곱셈이 덧셈이 되는 게 핵심이다. 앱이 하나 늘어도 +1이지 +4가 아니다. 그래서 GitHub이 공식 MCP 서버 하나 만들어두면 모든 AI 앱이 갖다 쓴다.

JDBC랑 똑같은 발상이다. JDBC 덕분에 MySQL에서 PostgreSQL로 바꿔도 코드가 거의 그대로고 드라이버만 갈아끼우면 되는 것처럼.

## MCP는 서버가 아니라 "규칙"이다

여기서 제일 헷갈렸던 부분. 자료를 찾아주는 건 **서버**고, MCP는 **그 서버랑 대화하는 규칙**이다.

톰캣으로 보면 바로 온다.

- **서버** = 톰캣에 올린 프로그램. 실제로 DB 뒤지고 결과 만드는 놈
- **HTTP** = 브라우저가 그 서버한테 말 거는 규칙. `GET /users/1` 이렇게 물어보기로 한 약속

톰캣이 HTTP는 아니다. MCP도 같은 관계다.

```
   AI  ──────────────────────→  서버
        "자료 찾아줘"                │
                                    │ (실제로 찾음)
   AI  ←──────────────────────      ↓
        내용

        └──────┬──────┘
          이 대화 방식이 MCP
```

MCP는 **화살표 위에 적힌 규칙**이지 양쪽 끝의 박스가 아니다.

## 풀네임과 출처

**Model Context Protocol**

| 단어 | 뜻 |
|---|---|
| Model | AI 모델 |
| Context | 맥락 = AI가 답할 때 참고할 자료 |
| Protocol | 규약, 약속 |

→ "AI 모델한테 자료를 건네주는 약속"

Anthropic(Claude 만든 회사)이 2024년 11월에 만들어서 **공개**했다. 자기들만 쓰는 게 아니라 규격을 통째로 열었고, 그래서 지금은 다른 회사들도 갖다 쓴다.

이게 중요하다. Anthropic 소유였으면 누가 만든 MCP 서버는 Claude에서만 됐을 거다. 공개했기 때문에 다른 AI 툴에서도 그대로 꽂힌다.

규격 문서: modelcontextprotocol.io

## 규칙이 구체적으로 뭐냐 - 딱 두 마디

```
1) "너 뭐 할 수 있어?"   →  tools/list
2) "그럼 이거 해줘"      →  tools/call
```

이게 핵심이다. JSON으로 주고받는다.

**1단계 - AI가 물어본다**

```json
{ "method": "tools/list" }
```

**서버 대답 - 자기가 할 수 있는 걸 알려준다**

```json
{
  "tools": [
    { "name": "search_docs", "description": "문서를 검색한다" },
    { "name": "create_doc",  "description": "문서를 새로 만든다" }
  ]
}
```

**2단계 - AI가 골라서 시킨다**

```json
{
  "method": "tools/call",
  "params": {
    "name": "search_docs",
    "arguments": { "query": "배포 가이드" }
  }
}
```

`method`에 뭘 원하는지 쓰고 서버가 답한다. HTTP에서 `GET /users/1` 하는 거랑 발상이 같다.

### 여기서 중요한 건

1단계를 보면, **AI는 그 서버가 뭘 할 수 있는지 미리 모른다. 물어본다.**

덕분에 서버에 기능을 새로 추가하면 AI가 다음에 물어볼 때 알아서 알게 된다. AI를 업데이트하거나 설정을 고칠 필요가 없다. **서버가 자기소개를 하고 AI가 그걸 듣고 쓰는 구조**다.

## 봉투는 규격, 알맹이는 만드는 사람

JSON 안의 내용을 누가 정하냐 하면, 나눠져 있다.

| MCP가 정한 것 (못 바꿈) | 서버 만드는 사람이 정하는 것 |
|---|---|
| `method` 이름 (`tools/list`, `tools/call`) | 툴 이름을 뭐라고 지을지 |
| 응답에 `tools` 배열이 온다는 것 | 툴을 몇 개 만들지 |
| 각 툴은 `name`, `description`, `inputSchema`를 가진다 | description을 뭐라고 쓸지 |

REST API랑 같다. HTTP는 `GET`/`POST`랑 상태코드를 정하지만, `/users/1`이라는 경로랑 응답 JSON 모양은 내가 정한다. MCP도 형식만 정해주고 내용은 내 맘이다.

```json
{
  "name": "search_docs",                  // ← 만든 사람이 지음
  "description": "문서를 검색한다",         // ← 만든 사람이 씀
  "inputSchema": {                         // ← 이 칸이 있어야 하는 건 MCP 규칙
    "type": "object",
    "properties": { "query": { "type": "string" } },
    "required": ["query"]
  }
}
```

`inputSchema`는 **JSON Schema**라는 기존 표준을 갖다 쓴 거다. MCP가 새로 만든 게 아니다.

### description은 주석이 아니라 프롬프트다

이게 실무에서 제일 중요한 것 같다. `description`은 사람 보라고 쓰는 게 아니라 **AI가 읽는다.** AI는 이 문장만 보고 "지금 이 툴을 써야 하나"를 판단한다.

```
"description": "검색"                      ← 나쁨. 뭘 검색하는지 AI가 모름
"description": "사내 문서를 제목과 본문     ← 좋음
                키워드로 검색해 반환한다"
```

대충 쓰면 AI가 엉뚱한 툴을 부르거나, 있는데도 안 쓴다.

## AI는 어떤 서버로 갈지 어떻게 정하나

서버를 여러 개 붙였을 때 AI가 어디로 갈지 판단하는 방식.

**결론부터: AI는 "서버"를 고르는 게 아니라 "툴"을 고른다.**

앱이 켜질 때 붙어 있는 **모든 서버한테 `tools/list`를 돌려서** 한 바구니에 합친다.

```
search_docs     "사내 문서를 검색한다"        ← 사내 서버
gmail_search    "Gmail에서 메일을 검색한다"   ← Gmail 서버
drive_search    "구글 드라이브 파일을 찾는다"  ← Drive 서버
```

AI 입장에서는 그냥 툴 목록 하나다. "이건 어느 서버 거"라고 나눠서 보지 않는다.

내가 "배포 가이드 뭐야?" 하면 AI가 목록을 훑고 **description을 읽어서** `search_docs`를 고른다. 실제 배달은 앱이 한다. 툴 이름 보고 어느 서버로 보낼지 알아서 찾아간다. 스프링 `@RequestMapping`이 경로 보고 컨트롤러 찾아가는 거랑 같다.

### 그래서 생기는 문제 두 가지

1. **이름이 겹치면 헷갈린다.** 사내 서버 툴이 그냥 `search`고 Drive에도 `search`가 있으면 엉뚱한 데 가서 찾는다. 그래서 `calculate` 말고 `calculator_arithmetic`처럼 구체적으로 지으라고 권한다.

2. **툴이 너무 많으면 성능이 떨어진다.** 서버 6개에 툴 10개씩이면 60개고, 그 목록이 매번 통째로 AI한테 전달된다. 토큰도 먹고 선택지가 많아 헷갈린다. 안 쓰는 서버는 꺼두는 게 낫다.

## 연결했다고 쓰는 게 아니다

이것도 착각하기 쉬웠던 부분. **MCP 서버를 연결하면 툴이 목록에 추가될 뿐 우선순위가 생기지 않는다.**

```
나:  "로그인 화면 만들어줘"
AI:  (목록 훑음) "딱히 검색할 필요 없겠는데?"  → 규칙 문서 안 보고 그냥 만듦
```

중점적으로 보게 하려면 **따로 지시해야 한다.** Claude Code는 `CLAUDE.md`를 매번 읽으니까 거기에 적어두면 된다.

```markdown
UI, 디자인, 문서 작업을 시작하기 전에
반드시 위키 MCP에서 관련 규칙을 먼저 조회한다.
```

**연결 = 능력을 준 것, CLAUDE.md = 그걸 쓰라고 시킨 것.** 둘 다 필요하다.

## "MCP 서버를 만든다"가 무슨 말이냐

MCP는 프로토콜인데 서버를 만든다는 게 이상해서 걸렸는데, 그냥 줄임말이었다.

> "MCP 서버" = **MCP 규격에 맞춰 말하는 서버**

"HTTP 서버 만든다"도 똑같이 이상하지만 다들 쓴다. 뜻은 "HTTP 규격으로 응답하는 서버"고 그게 톰캣이다. 프로토콜 이름을 앞에 붙여서 "얘는 이 말을 할 줄 안다"를 표시하는 관례다.

실제로 만드는 건 두 덩어리다.

```
┌─────────────────────────────────┐
│ ② MCP 규격으로 포장해서 내보내기  │  ← 이 부분만 MCP
├─────────────────────────────────┤
│ ① 자료 찾는 로직                 │  ← 그냥 평범한 코드
└─────────────────────────────────┘
```

①은 MCP랑 아무 상관 없는 보통 프로그램이다. 폴더 읽고 키워드 찾고 돌려주고.

코드로 보면 스프링이랑 판박이다.

```python
@mcp.tool()
def search_docs(query: str) -> str:
    """사내 문서를 검색한다"""      # ← AI가 읽는 description
    return 폴더에서_찾기(query)     # ← 그냥 평범한 코드
```

```java
@GetMapping("/docs")              // ← HTTP로 노출시켜줘
public String search(String q) {
    return 폴더에서_찾기(q);       // ← 그냥 평범한 코드
}
```

`@GetMapping` 붙였다고 HTTP를 구현한 게 아니듯, MCP도 **SDK가 JSON 주고받는 걸 대신 해준다.** 만드는 사람은 `tools/list`나 JSON 형식을 직접 안 건드린다.

그러니까 "MCP 서버 만들기"는 생각보다 작은 일이다. 대부분이 평범한 코드고 MCP는 껍데기 한 겹이다.

## 규격은 양쪽에 다 있어야 한다

서버 안에 "규격 문서"가 들어있는 건 아니다. **규격을 구현한 코드(SDK)**가 들어있는 거다. 톰캣 안에 HTTP RFC 문서가 있는 게 아니라 HTTP 처리 코드가 있는 것처럼.

그리고 규격은 서버에만 있는 게 아니다.

```
   AI 앱                          MCP 서버
   (클라이언트 쪽 구현)            (서버 쪽 구현)
        │                              │
        └────── 같은 규격을 각자 구현 ──┘
                  그래서 말이 통함
```

한국어랑 같다. 문법이 어디 한 곳에 저장돼 있어서 대화가 되는 게 아니라, **말하는 사람 양쪽 머릿속에 다 있어서** 통하는 거다.

그래서 서버 만든 사람이 AI 개발사랑 상의한 적이 없어도 그냥 붙는다. 공개된 규격 하나를 양쪽이 따랐으니까. 이게 표준의 힘이다.

반대로 **양쪽 버전이 어긋나면 말이 안 통한다.** MCP는 아직 스펙이 자주 바뀌는 편이라, AI 앱을 업데이트했더니 서버가 안 붙는 상황이 생길 수 있다. 그럴 땐 서버 쪽 SDK 버전을 의심해야 한다.

## Tools 말고 또 있는 것

서버가 내놓을 수 있는 건 세 종류다. 가르는 기준은 **"이걸 쓰자"고 누가 결정하느냐**다.

| | 누가 결정 | 뭐냐 |
|---|---|---|
| **Tools** | **AI**가 판단 | 실행되는 동작 |
| **Resources** | **사용자/앱**이 지정 | 읽으라고 건네주는 자료 |
| **Prompts** | **사용자**가 선택 | 미리 만들어둔 질문 양식 |

직원한테 시킨다고 생각하면 쉽다.

- Tools = "필요하면 알아서 자료실 뒤져봐" → 직원이 판단
- Resources = "이 서류 읽고 답해" 하고 서류를 건넴 → 내가 고름
- Prompts = 자주 쓰는 질문지 양식을 꺼내 씀 → 내가 꺼냄

실제로는 **Tools가 압도적으로 많이 쓰인다.** Resources랑 Prompts는 아예 지원 안 하는 AI 앱도 꽤 있다. 검색 툴 하나면 대부분 해결되기 때문에, "이런 것도 규격에 있구나" 정도로 알아두면 될 것 같다.

## 정리

1. AI는 사내 자료를 모른다
2. 그래서 서버를 두고 AI가 물어보게 한다
3. 그 서버랑 대화하는 **규칙**이 MCP다
4. JSON으로 "뭐 할 수 있어?" → "이거 해줘"를 주고받는다
5. 봉투 규격은 MCP가, 알맹이는 서버 만든 사람이 정한다
6. AI는 서버가 아니라 **툴**을 고른다. description 보고 판단한다
7. 연결만으로는 안 본다. 쓰라고 시켜야 한다

쓰는 입장에서 제일 기억할 건 6번과 7번인 것 같다. **"AI가 알아서 다 본다"가 아니라 "AI가 판단해서 고른다"**는 것.
