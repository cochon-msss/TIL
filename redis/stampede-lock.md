# 캐시가 비는 한순간 — 스탬피드와 분산 락

[캐시 고치나 지우나](cache-consistency.md)에서 TTL은 안전망이라고 했다. 그런데 TTL이 끝나는 **그 순간** 자체가 사고가 된다.

## 첫 사람만 가져오는 줄 알았다

메인 "인기글 목록" 캐시 TTL이 딱 끝났다. 초당 1만 명이 들어오는 중이다.

"첫 진입한 사람이 조회해 오고 그 이후부턴 Redis에서 가져가겠지"라고 했다. 틀렸다. **첫 사람이 가져오는 데 시간이 걸린다**는 걸 놓쳤다. 인기글 쿼리가 200ms 걸리면

```
0ms     요청1    Redis 없음 → DB 조회 시작 ......... 200ms 후 채움
1ms     요청2    Redis 없음 → DB 조회 시작
...
199ms   요청2000 Redis 없음 → DB 조회 시작
200ms   이제야 채워짐
```

요청1이 채우기 전까지 다들 Redis가 **비어 있는 걸 본다.** 2000개가 동시에 같은 무거운 쿼리를 던진다. DB가 느려지면 200ms가 2초가 되고, 그동안 2만 개가 몰리고… 악순환이다.

**캐시 스탬피드(cache stampede)**. 캐시가 막아주던 트래픽이 비는 한순간에 DB로 우르르.

## 나머지는 기다리게 — 근데 누가 첫 번째인지 어떻게 아나

해결은 내가 처음 틀리게 말한 그거다. 첫 사람만 DB 가고 나머지는 잠깐 기다렸다 Redis에서 가져간다.

문제는 2000개 요청이 **서로 다른 서버에서 서로 모른 채** 온다는 거다. 그래서 모두가 보는 곳(Redis)에 "지금 내가 가지러 감" 표시를 남긴다.

`SET 키 값 NX` — NX는 Not eXists, **키 없을 때만 저장**. 있으면 실패.

```
요청1:  SET lock:인기글 1 NX → 성공 → DB 조회 → 캐시 채움 → lock 삭제
요청2:  SET lock:인기글 1 NX → 실패 → 잠깐 기다렸다 Redis 다시 확인
```

[싱글 스레드](single-thread.md)라서 SET NX 2000개가 동시에 와도 **딱 하나만 성공**한다. 확인+쓰기가 명령 하나라 틈이 없다. 서버 여러 대가 같이 쓰는 락이라 **분산 락**.

```
요청 → Redis에 있음 → 가져감 (대부분)
     → 없음 → SET NX 성공 → DB → 채움 → 락 해제
             → SET NX 실패 → 50ms 기다림 → Redis 재확인 → 있으면 가져감
```

기다리기도 싫으면 옛날 값을 계속 보여주면서 뒤에서 한 명만 새로 만들어 바꿔 끼우는 방법도 있다. 인기글은 몇 초 늦어도 되니까.

## 락 잡은 서버가 죽으면

"AOF?"라고 했다. 아니다. AOF는 **Redis가** 죽었다 살아날 때 얘기고, 지금은 **서버A가** 죽었고 Redis는 멀쩡하다. 멀쩡하니까 락도 멀쩡히 남는다. 지울 사람이 없다.

```
요청2: SET NX 실패 → 대기 → 실패 → 대기 → … 영원히
```

필요한 건 지울 사람 없어도 알아서 사라지는 키 — **유효시간**이다.

```
SET lock:인기글 1 NX EX 5    ← 5초 뒤 자동 삭제
```

TTL만 세 번째다.

```
캐시   틀린 사본을 결국 사라지게
세션   로그인을 끝내는 게 목적
락     죽은 서버가 못 푼 락을 대신 풀어줌
```

## 남의 락을 지운다

TTL 5초인데 A가 죽은 게 아니라 DB가 느려서 7초 걸리면?

```
0s   A  락 획득 → DB 조회
5s   락 만료 → B 락 획득 → DB 조회     (둘이 동시에 일함)
7s   A  끝 → 캐시 채움 → DEL lock   ← 이건 B 락이다
7s   C  락 획득 → …                    연쇄 붕괴
```

5초에 B가 들어오는 건 맞췄다. 진짜 사고는 7초에 A가 **B의 락을 지우는** 거다. DEL은 누구 락인지 확인 안 한다.

처음엔 "락 걸려 있으면 지우지 마"를 넣으면 되지 않나 했다. 안 된다. 걸려 있다/없다로는 **누구 거인지** 모른다. 내 락이 살아 있어도 걸려 있는 건 똑같다.

그래서 값에 `1` 대신 서버별 고유값(UUID) — **이름표**를 넣는다.

```
A: SET lock:인기글 "A-uuid" NX EX 5
B: SET lock:인기글 "B-uuid" NX EX 5
7s A: GET → "B-uuid" → 내 거 아님 → 안 지움 ✅
```

근데 GET 확인 → DEL은 명령 두 개라 또 틈이다. Lua로 묶는다.

```lua
if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('DEL', KEYS[1])
end
return 0
```

## 5초에 다들 DB로 가는 거 아냐?

여기서 헷갈렸다. 5초 안에 못 다녀오면 2000개가 다 DB로 가고, 마지막 2000번째가 Redis에 넣는 줄 알았다.

아니다. 락 못 잡은 요청은 5초 지나도 **각자 DB로 안 간다.** "Redis 확인 → 없으면 SET NX 재시도"만 반복한다. 5초에 만료되면 1999개가 재시도하지만 싱글 스레드라 **하나만** 성공한다.

```
0s    요청1 락 → DB (7초)
5s    만료 → 요청57 하나만 락 → DB
7s    요청1 끝 → 채움 → 대기하던 애들 전부 Redis에서 가져감 ✅
12s   요청57 끝 → 같은 값 덮어씀 (문제없음)
```

DB 간 건 **2개**. 그리고 마지막 사람이 아니라 **처음 끝낸 사람**이 넣는 순간 다들 쓴다.

## TTL 길이 딜레마

그럼 넉넉하게 60초로? A가 0초에 **진짜 죽으면** — "7초"라고 했는데 아니다. 7초는 A가 살아서 끝냈을 때 얘기다. 죽었으면 아무도 안 채운다.

```
0s    A 락(60초) → 죽음
60s   락 만료 → 한 명 획득 → DB
67s   채워짐 → 이제야 인기글 보임
```

**67초** 동안 아무도 못 본다. 실제론 대기하다 에러 화면.

```
짧게 (5초)    죽은 락 빨리 풀림 ✅   느린 서버 일 중에 만료 → 둘이 동시에 ❌
길게 (60초)   느린 서버도 안전 ✅    죽은 락 오래 남음 → 다 오래 대기 ❌
```

근본 원인은 Redis가 **"느린 서버"와 "죽은 서버"를 구분 못 한다**는 거다. 둘 다 "아직 락 안 풀었음"으로만 보인다.

그래서 TTL은 짧게 잡고, 살아 있는 서버가 일하는 동안 **주기적으로 연장**한다. "나 아직 살아서 일하는 중". 살아 있으면 계속 연장, 죽으면 연장이 멈춰서 금방 풀린다. Redisson이 자동으로 해주는데 이걸 **워치독(watchdog)**이라고 부른다.

```
SET NX        싱글 스레드라 딱 하나만 성공
EX (TTL)      죽은 서버 락 대신 풀어줌
UUID 값       누구 락인지 이름표
Lua 해제       확인+삭제 틈 없앰
워치독         느린 서버 vs 죽은 서버 구분
```
