# DB가 바뀌면 캐시는 고치나 지우나

[Redis 메모리](redis-memory.md), [싱글 스레드](single-thread.md) 노트에 이어서.

사용자 정보를 캐시해 두고 있다.

```
DB      user:7 닉네임 = "철수"
Redis   user:7 닉네임 = "철수"   (DB 사본)
```

닉네임을 "영희"로 바꿨고 DB는 먼저 고쳤다. Redis 사본은 어떻게 하나.

```
A. 캐시도 "영희"로 고친다   (SET)
B. 캐시를 지운다            (DEL) → 다음 조회 때 DB에서 다시 채워짐
```

A가 좋아 보인다. 바로 최신값이고 다음 조회 때 DB 갈 필요도 없다. 그런데 실무는 B를 쓴다.

## A는 순서가 뒤집히면 틀린 값이 남는다

왜 B냐는 질문에 "DB가 더 정확하니까, 싱글 스레드 때문에 원자성이 깨질 수 있어서"라고 했다. 앞 절반은 맞고 뒤는 틀렸다. `SET` 하나하나는 원자적이다. 문제는 **DB와 Redis, 서로 다른 두 곳을 차례로 고친다**는 거다. 그 사이에 다른 서버가 낀다.

서버 두 대가 거의 동시에 "영희", "민수"로 바꾼다.

```
서버1 (영희)              서버2 (민수)
① DB = 영희
                          ② DB = 민수
                          ③ Redis = 민수
④ Redis = 영희   ← 늦게 도착

결과:  DB = 민수,  Redis = 영희   ❌
```

에러도 안 난다. TTL 끝날 때까지 조용히 틀린 닉네임이 보인다.

B로 하면

```
서버1 (영희)              서버2 (민수)
① DB = 영희
                          ② DB = 민수
                          ③ Redis 삭제
④ Redis 삭제

결과:  DB = 민수,  Redis = (없음) → 다음 조회 때 "민수" 채워짐 ✅
```

## 왜 DEL은 순서를 안 타나

"삭제가 하나의 덩어리로 실행되니까"라고 했는데 아니다. A의 SET도 각각 덩어리로 실행됐는데 깨졌다.

차이는 **명령이 값을 들고 가느냐**다.

```
SET = 영희 / SET = 민수   서로 다른 값을 주장 → 마지막에 도착한 게 이김 → 순서가 결과를 바꿈
DEL / DEL                둘 다 "여기 값 없음" → 같은 말 → 순서 바꿔도 결과 같음
```

DEL은 "이 사본 이제 못 믿음, 정답은 DB 가서 봐"라고 하고 **값 결정을 DB한테 넘긴다.**

몇 번 해도, 어떤 순서로 해도 결과가 같은 성질을 **멱등성(idempotency)**이라고 한다.

## B도 구멍이 있다

조회하면서 캐시를 채우는 서버가 끼면

```
조회 서버                    수정 서버
① Redis 없음 → DB 조회 → "철수" 받음
                             ② DB = 영희
                             ③ Redis 삭제
④ Redis = "철수" 채움
```

**철수가 남는다.** [재고](single-thread.md)랑 같은 모양이다. 확인한 값이 쓰는 순간엔 이미 낡았다. DEL이 잘못한 게 아니라 조회 서버가 들고 있던 값이 낡았다.

그래도 A보단 훨씬 드물다. ①의 "조회→채우기"가 ②③의 "수정→삭제"보다 **오래** 걸려야 터지는데, 보통 조회가 수정보다 빠르다. 완벽하진 않고 깨질 확률이 낮은 방법이다.

읽을 때 없으면 채우고, 수정하면 지우는 이 방식을 **Cache-Aside**라고 한다.

## 그래도 영원히 남진 않는다 — TTL

드물게 철수가 남아도 **유효시간이 끝나면 사라진다.** TTL은 메모리 비우는 장치이기 전에 **최후의 안전망**이다.

```
수정 시 SET    값을 들고 감 → 순서 뒤집히면 틀린 값이 남음
수정 시 DEL    값 안 들고 감(멱등) → 순서 상관없음 → 그래도 "낡은 값 늦게 채우기"는 드물게
TTL           그것마저 결국 사라지게 함
```

캐시는 "항상 정확"을 포기하고 **"잠깐 틀릴 수 있지만 결국 맞춰진다"**를 고른 거다. 최종 일관성(eventual consistency).

## TTL은 얼마로

1초로 잡으면? 정합성은 맞는데 거의 다 DB로 가니까 캐시 의미가 없다. 그냥 DB 조회하는 게 낫다.

```
짧게   정확 ↑   캐시 효과 ↓ (DB 부담 ↑)
길게   정확 ↓   캐시 효과 ↑ (DB 부담 ↓)
```

정답 숫자는 없고 기준은 **"이 데이터가 얼마 동안 틀려도 괜찮은가"**다.

```
인기글 목록   몇 분 늦어도 모름         → 길게
상품 가격     틀리면 돈 문제            → 짧게, 수정 시 바로 DEL
재고 수량     틀리면 초과 판매          → 캐시에 의존 안 함 (Lua)
```
