# DHCP

[ARP](arp.md) 노트 끝에 "RARP는 지금 거의 안 쓴다, DHCP가 가져갔다"고 적어놨는데 정작 DHCP는 안 봤다. 그걸 봤다.

생각보다 헷갈리는 게 많았다. 특히 **게이트웨이가 어디까지 관여하는지**를 계속 틀렸다.

## IP가 없는데 어떻게 IP를 요청하나

여기서 바로 막혔다.

IP를 받으려면 서버한테 요청을 보내야 한다. 근데 패킷을 만들려면 주소를 적어야 한다.

```
출발지 IP:  ???   ← 아직 없다
목적지 IP:  ???   ← 서버가 어딨는지도 모른다
```

둘 다 모른다. 닭이 먼저냐 알이 먼저냐다.

답은 특수 주소 두 개다.

```
출발지 IP:  0.0.0.0            "나 아직 주소 없음"
목적지 IP:  255.255.255.255    "이 대역 전체에게"
```

**ARP에서 쓰던 방법과 같다.** ARP 노트에 "같은 대역 전체에 방송한다"고 적었는데 그거다. 상대가 누군지 모를 때 다 들리게 외치기.

그리고 외칠 수 있는 이유가 하나 있다.

```
IP   없음  (받으러 온 것)
MAC  있음  (랜카드에 박혀 있음)
```

**IP는 없는데 MAC은 공장에서 나올 때부터 있다.** 같은 대역 안에서는 MAC만 있으면 통신이 되니까(2계층) 요청을 보낼 수 있다.

ARP 노트에 적은 RARP 상황과 똑같은 모양이다. "아는 건 랜카드에 박힌 자기 MAC뿐"이라던 그거.

## 0.0.0.0은 "계속 요청 중"이라는 뜻이 아니다

처음엔 `0.0.0.0`이 "할당을 못 받아서 계속 재시도하는 상태"를 뜻하는 건가 싶었다. 아니다.

**헤더의 칸을 비워둘 수 없어서 넣는 값이다.**

```
IP 패킷 헤더
┌──────────────────┐
│ 출발지 IP (4바이트) │  ← 반드시 채워야 한다
│ 목적지 IP (4바이트) │
└──────────────────┘
```

4바이트 고정 칸이라 안 적을 수가 없다. 그래서 "없음"을 뜻하는 값을 약속해둔 거다. 서류 빈칸에 "해당없음"이라고 적는 것과 같다.

그러니까 재시도 횟수랑 무관하다.

```
첫 번째 요청   출발지 0.0.0.0
열 번째 요청   출발지 0.0.0.0    똑같다
```

**주소가 없는 동안은 계속 `0.0.0.0`** 이다.

갱신(뒤에 나온다)과 비교하면 선명하다.

```
처음 받을 때   출발지 0.0.0.0          주소가 없다
갱신할 때      출발지 192.168.0.130    주소가 있다
```

주소를 아느냐 모르느냐가 패킷 모양을 정한다.

## 서버는 게이트웨이가 아니라 MAC으로 답한다

내가 주소가 없으면 서버는 어디로 답을 보내나. **게이트웨이로 보내는 줄 알았다.** 아니다. 그럴 수가 없다.

게이트웨이를 쓴다고 가정하면 순환이 된다.

```
DHCP 가 게이트웨이를 쓴다면
  → 게이트웨이 주소를 알아야 한다
  → 그 주소를 알려주는 게 DHCP 다
  → DHCP 가 먼저 돌아야 알 수 있다
  → 그런데 DHCP 가 게이트웨이를 쓴다면...
```

자기 자신이 필요해진다. 그래서 **DHCP는 게이트웨이 없이 동작하도록 설계돼야 한다.** 안 그러면 처음에 아무것도 시작할 수 없다.

실제로는 요청 패킷 안에 내 MAC이 들어 있다.

```
DHCP Discover
┌────────────────────────────────┐
│ 출발지 IP : 0.0.0.0             │  주소 없음
│ 목적지 IP : 255.255.255.255     │  다 들리게
│ 내 MAC    : aa:bb:cc:dd:ee:ff   │  ← 이걸로 나를 찾는다
└────────────────────────────────┘
```

서버는 이 MAC을 보고 답을 돌려보낸다. 같은 대역이니 MAC만 있으면 전달된다.

**IP가 없는 동안 나를 식별하는 수단이 MAC이다.**

## DHCP는 대역 안에서 끝나는 대화다

위의 순환 얘기가 요청 방향에도 그대로 적용된다. DHCP 요청은 게이트웨이를 안 거친다.

라우팅 노트에 적은 규칙이 그대로다.

```
목적지가 같은 대역   →  직접 보낸다
목적지가 다른 대역   →  게이트웨이에 넘긴다
```

DHCP 서버는 **같은 대역에 있다.** 브로드캐스트가 닿는 범위가 곧 같은 대역이고, 거기서 답한 놈이니까. 그러니 첫 번째 줄이다.

```
내 PC  ←──────→  공유기(DHCP 서버)
        같은 대역. 직접 주고받는다
```

같은 집 안에서 옆방 사람한테 말할 때 현관문을 안 쓰는 것과 같다. **게이트웨이는 현관문이다.**

여기서 따라오는 결론이 있다. **DHCP 서버는 반드시 같은 대역에 있어야 한다.** ARP 노트에 적은 "방송이 대역 밖으로는 안 나간다"가 여기도 걸리니까. 집에서는 공유기가 그 역할을 한다.

## 서버가 누구냐 — 공유기다

"DHCP 서버"라니까 어딘가 전용 장비가 있는 줄 알았다. 아니다. **이미 있는 장비에 켜져 있는 기능이다.**

집에서는 공유기 한 상자가 여러 역할을 겸한다.

```
공유기 (192.168.0.1)
  ├─ 게이트웨이      밖으로 나가는 문
  ├─ 스위치          집 안 기기들 연결
  ├─ DHCP 서버       IP 나눠주기
  ├─ DNS 포워더      이름 물어보면 대신 물어봐주기
  └─ NAT             사설 IP ↔ 공인 IP 변환
```

이미 다른 노트에 적어둔 패턴이다. [DNS](dns.md) 노트의 "공유기가 DNS 서버이기도 하다", [라우팅](routing.md) 노트의 "게이트웨이는 장비 종류가 아니라 역할이다" — **DHCP 서버도 똑같이 역할이다.**

실제로 거기 있는지 찍어봤다.

```
> Test-Connection 192.168.0.1
응답시간 : 1ms, 0ms

> Get-NetNeighbor -IPAddress 192.168.0.1
192.168.0.1   04-D5-90-xx-xx-xx   Reachable
```

ARP 노트에 찍었던 줄과 같은 거다.

```
당시 노트:  192.168.219.1   dc:70:35:1a:bb:45   ...   1169
지금:       192.168.0.1     04-D5-90-xx-xx-xx   Reachable
```

MAC 앞 3바이트가 제조사 코드다. OUI 조회하면 어느 회사 장비인지 나온다.

### 반드시 같은 장비는 아니다

회사 망에서는 분리하는 경우가 많다. 라우터는 라우터고 DHCP는 따로 둔다.

```
집:     게이트웨이 192.168.0.1    DHCP 서버 192.168.0.1    같다
회사:   게이트웨이 10.0.0.1       DHCP 서버 10.0.0.50      다르다
```

`ipconfig /all`에 게이트웨이와 DHCP 서버가 **따로 찍히는** 이유가 이거다. 집에서는 같은 값이라 왜 두 줄인지 의아했는데, 원래 다를 수 있는 값이라서 칸이 두 개다.

## 내 PC는 DHCP를 안 쓰고 있었다

찍어보고 알았다.

```
어댑터   : Realtek PCIe GbE Family Controller
IP       : 192.168.0.130
DHCP켜짐 : False        ←
DHCP서버 : (없음)
임대시작 : (없음)
```

고정 IP로 손으로 넣어놨다. 그래서 DHCP 서버 칸이 비어 있다. 물어본 적이 없으니 답해준 서버도 없다. DNS가 `8.8.8.8`인 것도 직접 적은 값이다.

```
DHCP 쓰는 기기   공유기에 물어봐서 받는다  →  DHCP 서버 주소가 찍힌다
고정 IP 기기     안 물어본다               →  칸이 비어 있다
```

그리고 ARP 노트에 적어둔 IP 충돌 위험이 **내 얘기였다.**

> 주로 누가 고정 IP를 손으로 넣었는데 그게 DHCP가 다른 기기한테 준 IP랑 겹칠 때 생긴다.

`192.168.0.130`을 손으로 넣었으니, 공유기가 나눠주는 범위에 `.130`이 포함돼 있으면 다른 기기한테 같은 주소를 줄 수 있다. 공유기 설정에서 범위를 확인해봐야 한다.

## DORA — Request가 왜 필요한가

주고받는 게 두 번씩, 총 네 번이다. 앞 글자를 따서 DORA.

```
내 PC                         서버
  │  Discover  →               │   "거기 누구 없어요? IP 필요해요"
  │       ← Offer              │   "192.168.0.130 어때요?"
  │  Request   →               │   "그거 쓸게요"
  │       ← Ack                │   "확정. 쓰세요"
```

여기서 이상했다. **Offer를 받았으면 끝 아닌가.** 서버가 "`.130` 써라"고 알려줬는데 왜 또 "그거 쓸게요"를 보내나.

**서버가 여러 대 있을 수 있어서다.**

Discover는 브로드캐스트다. 서버가 두 대면 둘 다 듣고 둘 다 답한다.

```
내 PC  ──Discover──▶  (대역 전체)
                      ├─ 서버A: "192.168.0.130 어때요?"
                      └─ 서버B: "192.168.0.77 어때요?"
```

제안이 두 개 왔고 하나만 써야 한다. 문제는 **서버A도 `.130`을 빼놨다는 것**이다. 제안한 순간부터 "이건 누가 쓸 예정"으로 잡아둔다. 안 그러면 그 사이에 다른 기기한테 같은 주소를 줘버린다.

그래서 B를 골랐으면 A에게도 알려줘야 한다.

```
내 PC  ──Request(서버B 걸로 할게요)──▶  (대역 전체)
                                        ├─ 서버A: "아 그럼 .130 풀어야겠네"
                                        └─ 서버B: "오케이, 확정(Ack)"
```

Request도 브로드캐스트로 보내고 안에 "서버B의 제안을 받겠다"고 적는다.

**Request는 B에게 하는 수락이면서 동시에 A에게 하는 거절이다.** 그래서 한 단계가 더 필요하다.

## 자동 할당일 때만 DORA를 한다

이 4단계는 "자동으로 IP 받기"로 설정돼 있을 때만 돈다.

```
자동 할당 (DHCP)  →  DORA 4단계를 거친다
고정 IP           →  아무것도 안 보낸다. 설정값을 바로 쓴다
```

고정 IP는 물어볼 필요가 없다. 이미 답을 적어놨으니까. 내 PC의 실제 랜카드는 고정이라 **DORA를 한 번도 안 했다.**

다만 완전히 조용한 건 아니다. ARP 중복 확인은 여전히 한다.

```
DHCP     Discover → Offer → Request → Ack    + ARP 중복 확인
고정 IP  (없음)                               + ARP 중복 확인
```

ARP 노트에 적은 "IP를 받으면 '이 IP 내가 쓴다'고 한 번 외쳐본다"가 그거다. **IP를 어디서 얻었는지는 달라도 겹치는지 확인하는 건 똑같이 한다.** 받는 절차와 검증은 별개다.

## 고르는 건 내가 아니라 서버다

"브로드캐스트로 요청하고 안 쓰는 IP를 자동 할당해서 쓴다"로 이해했는데, **주체가 틀렸다.**

내가 빈 IP를 찾아서 가져가는 게 아니다. **서버가 골라서 배정해준다.**

```
내 PC   "IP 좀 줘"              ← 요청만 한다
서버    "192.168.0.130 써"      ← 고르는 건 서버
```

서버가 표를 들고 있다. "나눠줄 범위는 `.100 ~ .200`이고 지금 `.107`까지 나가 있다" 같은 걸 관리한다. 거기서 안 쓰는 걸 꺼내 준다.

**내 PC는 빈 IP가 뭔지 모른다.** 알 방법도 없고 알 필요도 없다.

그래서 169.254(뒤에 나온다)와 정반대다.

| | 누가 고르나 | 어떻게 |
|---|---|---|
| DHCP | 서버 | 관리 표에서 꺼내 준다 |
| `169.254` | 내 PC | 랜덤 + ARP로 중복 확인 |

표를 관리하는 쪽이 있으니 DHCP는 겹칠 일이 없고, `169.254`는 관리자가 없으니 ARP로 매번 물어봐야 한다.

## 받은 IP는 내 것이 아니라 빌린 것이다

ARP 노트 표에 "빌려주고 기한 지나면 회수"라고 적어뒀는데, 왜 그렇게 만들었는지가 이번에 풀렸다.

**기기가 떠나는 걸 서버가 알 방법이 없어서다.**

노트북을 들고 카페를 나갈 때 "저 반납합니다" 하고 알려주지 않는다. 그냥 끊기고 사라진다. 전원을 뽑아도 마찬가지다.

서버 입장에서는 이 둘이 구분이 안 된다.

```
① 잠깐 자리 비웠다 (계속 쓸 거다)
② 아예 떠났다     (다시 안 온다)
```

둘 다 "조용하다"로 똑같이 보인다. 그래서 기한을 걸어둔다.

```
기한 내에 연락 옴   →  계속 쓰는 중. 연장
기한 지나도 조용함  →  떠난 걸로 판단. 회수해서 다른 기기에 줌
```

**떠났다고 알려주는 대신 살아 있으면 알려달라로 뒤집은 거다.**

### 그래서 IP가 다 떨어진다

카페를 생각하면 바로 나온다.

```
나눠줄 범위: 192.168.0.100 ~ 192.168.0.200   →  101개
임대 기간:   24시간

하루에 손님 150명이 와서 10분씩 쓰고 나간다
→ 나간 손님의 IP도 24시간 동안 묶여 있다
→ 101개가 금방 소진
→ 그 뒤에 온 손님: 169.254
```

**실제로 쓰는 기기는 몇 대 없는데 IP가 마른다.** 떠난 기기들이 자리를 붙잡고 있어서다.

그래서 임대 기간을 쓰임새에 맞춰 정한다.

```
공공 와이파이  짧게 (10분~1시간)   회전이 빠르다
사무실·집     길게 (하루~며칠)     계속 같은 기기
```

**임대 기간은 "기기가 얼마나 자주 바뀌냐"로 정한다.**

## 갱신 — 그래서 IP가 안 바뀐다

기한이 24시간이면 하루마다 IP가 바뀔 것 같은데 안 바뀐다. 중간에 갱신한다.

```
0시간    Ack 받음. "24시간 쓰세요"
12시간   "계속 쓸게요" → "네, 다시 24시간"   ← 갱신
24시간   (여기까지 안 간다)
```

갱신은 4단계를 다시 안 한다. 두 번으로 끝난다.

```
처음:  Discover → Offer → Request → Ack     (4번)
갱신:                     Request → Ack     (2번)
```

Discover가 필요 없는 이유는 **서버를 이미 알기 때문**이다. 처음에는 누가 있는지 몰라서 외쳤지만 지금은 아니까 그쪽에만 직접 보낸다. 브로드캐스트도 안 한다.

### 왜 하필 절반인가

**재시도할 여유를 남기려고다.**

만료 직전에 시도했다가 실패하면 그대로 끝이다. 절반 지점에 하면 실패해도 남은 절반 동안 또 시도할 수 있다.

```
12시간  갱신 시도  →  실패 (서버가 잠깐 바빴다)
21시간  다시 시도  →  실패
24시간  만료 → IP 포기 → 169.254
```

두 번째 시도는 브로드캐스트로 보낸다. 원래 서버가 죽었을 수도 있으니 "아무 서버나 받아주세요"로 바꾸는 거다.

### 그럼 IP가 바뀌는 건 왜

**기기를 꺼둔 사이에 기한이 지나서다.**

```
금요일 퇴근  PC 끔. 갱신할 사람이 없다
토요일       기한 만료 → 서버가 회수
             다른 기기에 그 IP를 줄 수 있다
월요일 출근  처음부터 다시 받음 → 다른 IP일 수 있다
```

주말 지나고 오니 IP가 달라져 있는 게 이거다. 쭉 켜두면 안 바뀐다.

## 실패는 "IP가 없는 것"이 아니라 "답이 안 온 것"이다

여기서 한참 헷갈렸다. DHCP는 IP가 없을 때 쓰는 건데, IP가 없는 게 이미 실패 아닌가 싶었다.

**IP가 없는 건 실패가 아니라 출발점이다.** 모든 기기가 켜질 때 IP가 없다. 정상이다.

실패는 물어봤는데 답이 안 온 것이다.

```
① 켜짐            IP 없음         ← 정상 출발점
② "IP 좀 줘" 외침  (MAC으로 가능)  ← 여기까지는 된다
③ 서버가 답함      "이거 써"       ← 이게 안 오면 실패
④ IP 받음          192.168.0.130
```

핵심은 **②와 ③이 다른 일**이라는 거다. IP가 없어도 질문은 보낼 수 있다. 하지만 답이 온다는 보장은 없다.

전입신고 같은 거다. 주소가 없어서 신고하러 가는 건 정상이고, 가서 신고하는 것도 가능하다. **사무실이 닫혀 있으면** 실패다. 주소가 없는 건 처음부터였고 실패한 건 신고가 안 받아들여진 것이다.

### "통신 실패"로 묶으면 진단을 놓친다

실패 원인이 세 가지인데 성격이 다르다.

```
① 선/와이파이가 안 붙음   →  외침이 아무 데도 안 간다       (통신 실패)
② DHCP 서버가 죽음        →  외침은 가는데 들을 사람이 없다
③ 줄 IP가 다 떨어짐       →  듣고도 못 준다
```

②와 ③은 **선이 멀쩡하다.** 랜선도 꽂혀 있고 스위치 불도 들어오고 같은 대역의 다른 기기와는 통신도 된다. 그런데 IP를 못 받는다.

`169.254`를 봤을 때 선만 확인하고 끝내면 ②·③을 못 찾는다.

## 169.254 — DHCP로 받은 게 아니라 실패했을 때 붙는 것

`169.` 대역을 보고 "DHCP로 할당받은 IP인가" 했는데 **정반대였다.**

```
DHCP 성공  →  192.168.0.130  같은 주소를 받는다
DHCP 실패  →  169.254.x.x    OS 가 스스로 붙인다
```

`169.254`가 보이면 "할당받았다"가 아니라 **"할당을 못 받았다"** 는 신호다.

이 대역 이름이 **링크 로컬(link-local)** 이고 윈도에서는 APIPA라고 부른다. 윈도 전용은 아니고 맥·리눅스도 같은 걸 한다.

정하는 방법이 재밌다. 서버가 없으니 **스스로 고른다.**

```
① 169.254.x.x 중에서 랜덤으로 하나 고른다
② "이 IP 내가 쓸게" 하고 ARP 로 외쳐본다
③ 아무도 대답 안 하면 → 그걸 쓴다
   누가 대답하면    → 다른 번호로 다시
```

②가 ARP 노트에 적은 그 동작이다. 서버가 없어도 겹치지만 않게는 할 수 있다.

### IP만 있다

```
IP            ✅  스스로 정했다
서브넷 마스크  ✅  /16 고정
게이트웨이     ❌  아무도 안 알려줬다
DNS           ❌  아무도 안 알려줬다
```

ARP 노트의 RARP 설명과 정확히 같은 한계다 — "IP만 알려줬다. IP만 있으면 인터넷을 못 한다."

### 실제로 내 PC에 있었다

```
어댑터   : Hyper-V Virtual Ethernet Adapter #2
IP       : 169.254.17.25      ← 자가 할당
DHCP켜짐 : True               ← 물어보려고 했다
임대시작 : 2026-10-13 11:28:08
임대만료 : 2026-10-13 11:28:08   ← 시작과 만료가 같다
```

`DHCP켜짐`이 `True`니까 물어보긴 했다. 근데 답이 안 왔다. **임대 시작과 만료가 같은 시각인 게 "받은 게 없다"는 표시다.** 가상 스위치라 DHCP 서버가 없는 게 정상이니 문제는 아니다.

### 왜 하필 169인가

숫자 자체에 의미는 없다. IANA가 `169.254.0.0/16`을 이 용도로 예약했고 모든 OS가 그 약속을 따르는 거다.

중요한 건 **"예약된 전용 블록"이라는 사실**이고 이유가 둘이다.

- **겹치면 안 되니까.** 아무 주소나 골랐다면 그게 그 망에서 실제로 쓰이는 주소일 수 있다. 전용 블록이면 아무도 안 쓰니 그 걱정이 없다.
- **보면 바로 알 수 있으니까.** `169.254`가 찍히면 "DHCP 실패"라고 즉시 판단된다. 진단 신호 역할이다.

그리고 라우터는 이 대역을 전달하지 않도록 규정돼 있다. **외부통신이 안 되는 게 사고가 아니라 설계다.** "이 주소는 이 선 안에서만 유효하다"는 뜻으로 만들었으니까. 그래서 이름이 링크 로컬 — 링크(선) 안에서만.

### 169.254로 게이트웨이에 보내면 되지 않나

안 된다. 두 겹이다.

**① 게이트웨이 주소를 모른다.** 그것도 DHCP가 알려주는 값이다. 라우팅 노트에 적은 `default` 줄이 아예 없는 상태다. 보낼 곳을 모르니 요청을 만들 수조차 없다.

**② 주소를 알아도 안 된다.** 이게 더 근본적이다.

```
내 IP    169.254.17.25   /16  →  169.254.x.x 대역
공유기   192.168.0.1          →  192.168.0.x 대역
```

**서로 다른 대역이다.** [서브넷](ip-subnet-port.md) 규칙이 여기 걸린다.

```
"192.168.0.1 로 보내야 하는데, 그건 다른 대역이네"
"다른 대역이면 게이트웨이로 넘겨야 하는데..."
"그 게이트웨이가 192.168.0.1 인데..."
```

순환이다. 게이트웨이에게 말을 걸려면 같은 대역에 있어야 하는데 없다. ARP로도 안 된다. "방송이 대역 밖으로는 안 나가니까" 공유기 MAC을 물어볼 방법이 없다.

그래서 `169.254`는 **같은 `169.254` 대역 기기끼리만** 통신된다. 두 대를 랜선으로 직결했을 때 같은 경우다.

## DHCP가 없어도 외부통신은 된다

"그럼 DHCP 서버가 없으면 영원히 외부통신이 안 되는 거네"라고 정리했는데 두 군데가 틀렸다.

**첫째, 영원히가 아니다.** OS가 포기하지 않는다. `169.254`를 붙여둔 상태에서도 백그라운드에서 계속 Discover를 재시도한다.

```
169.254 붙임  →  계속 "IP 좀 줘" 재시도
              →  서버가 살아나면 정상 IP 받음
              →  169.254 사라짐
```

공유기를 재부팅했을 때 잠깐 안 되다가 가만 두면 돌아오는 게 이거다. `169.254`는 **"대기 중"에 가깝다.**

**둘째, 고정 IP로 넣으면 된다.**

```
자동 할당 + DHCP 서버 없음  →  169.254        →  외부통신 ❌
고정 IP   + DHCP 서버 없음  →  내가 적은 값   →  외부통신 ✅
```

DHCP가 하는 일은 **값을 대신 알려주는 것**뿐이다. 통신 자체에 DHCP가 필요한 게 아니다. 값만 채워지면 된다. 내 PC가 그 경우다 — DHCP를 한 번도 안 썼는데 인터넷이 된다.

### DHCP가 죽으면 게이트웨이도 없는 건가

"DHCP가 공유기에 있다면서, DHCP 서버가 없으면 게이트웨이도 없는 거 아닌가" 싶었다. **맞는 경우도 있는데 항상은 아니다.**

```
①  공유기 없음/꺼짐     DHCP ❌   게이트웨이 ❌
②  DHCP 만 꺼짐         DHCP ❌   게이트웨이 ✅   ← 이게 있다
③  정상                 DHCP ✅   게이트웨이 ✅
```

공유기 설정에 **DHCP 서버 기능을 끄는 체크박스**가 있다. 끄면 IP를 안 나눠주는데 라우팅은 계속 한다. 역할들이 서로 독립적이라서다. 공유기를 두 대 연결할 때 뒤쪽 DHCP를 끄는 게 실제 사례다. 안 끄면 두 대가 서로 다른 IP를 나눠줘서 꼬인다.

그리고 더 중요한 건 **DHCP가 "정보 전달"이라는 점**이다.

```
공유기            거기 물리적으로 있다
게이트웨이 주소    192.168.0.1        ← 내가 알아야 하는 정보
DHCP              그 정보를 알려주는 심부름꾼
```

**DHCP가 죽으면 "알려줄 사람"이 없어진 거다. 장비가 사라진 게 아니다.** 공유기는 여전히 `192.168.0.1`에 있고 패킷을 받아 넘길 준비가 돼 있다. 내가 그 주소를 모르는 것이 문제다.

그래서 고정 IP로 적는 게 먹힌다. 장비가 없으면 적어도 소용없다. **존재와 통보가 별개라서** 적는 게 통하는 거다.

---

DHCP 공부하면서 제일 많이 틀린 게 게이트웨이였다. "밖으로 나가는 건 게이트웨이를 거친다"가 몸에 붙어 있어서 DHCP도 거기로 가는 줄 알았다.

근데 DHCP는 **게이트웨이 주소를 알려주는 쪽**이다. 알려주는 게 자기가 알려줄 값을 필요로 하면 시작을 못 한다. 그래서 같은 대역 안에서, 브로드캐스트로, MAC만 가지고 끝나도록 만들어져 있다.

`169.254`도 같은 이야기다. 주소를 못 받았으니 게이트웨이도 못 받았고, 그래서 선 안에서만 쓸 수 있는 주소가 붙는다. 외부통신이 안 되는 게 아니라 **애초에 선 밖을 전제하지 않은 주소**다.
