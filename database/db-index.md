# DB 인덱스랑 쿼리 성능

ES에서 문서 많으면 다 읽느라 느려지는 걸 겪고 나서, RDBMS는 어떤가 싶어서 인덱스를 정리해봤다. 결국 같은 얘기더라 - 읽어야 할 양을 어떻게 줄이냐.

## 인덱스가 뭐냐

책에서 단어 하나 찾는다고 생각하면 쉽다.

- 인덱스 없으면: 1페이지부터 끝까지 한 장씩 넘기면서 찾는다. 책 두꺼워지면(데이터 많아지면) 그만큼 오래 걸림. 이게 풀스캔(`Seq Scan`).
- 인덱스 있으면: 책 뒤 찾아보기 보고 "372쪽" 하고 바로 펼친다. 이게 인덱스 스캔(`Index Scan`).

DB 인덱스도 딱 이거다. 특정 컬럼을 미리 정렬해둔 색인을 만들어놓고, 조회할 때 테이블 전체를 훑는 대신 색인 타고 바로 찾아간다.

## B-Tree는 왜 빠른가

인덱스는 내부적으로 B-Tree라는 정렬된 트리로 돼있다.

```
              [ M ]              뿌리: M보다 작으면 왼쪽, 크면 오른쪽
            /       \
        [ F ]       [ T ]        가지: 더 잘게 나눔
        /   \       /   \
     [A~E][G~L]  [N~S][U~Z]      잎: 실제 값 + 테이블 위치
```

`홍길동` 찾으면 뿌리에서 "M보다 큼 -> 오른쪽", "T보다 작음 -> 왼쪽" 이런 식으로 위에서 몇 단계 내려가면 도달한다. 100만 건이어도 보통 3~4단계면 끝난다.

핵심은 O(log n)이라는 거. 데이터가 2배 10배 늘어도 단계 수는 거의 안 늘어난다. 그래서 데이터 많을수록 풀스캔이랑 격차가 벌어진다. 풀스캔은 데이터 2배면 시간도 2배니까.

몇 개 더:

- B는 Binary 아니라 Balanced(균형)다. 어느 잎으로 가든 깊이가 똑같이 유지돼서 최악의 경우에도 성능이 보장됨. 실제 DB들은 잎끼리 옆으로 연결된 B+Tree를 쓴다.
- 잎 노드가 정렬돼서 옆으로 이어져 있다. 그래서 등호(`=`)뿐 아니라 범위 검색(`BETWEEN`, `>`, `<`)이랑 `ORDER BY` 정렬도 인덱스로 빠르게 된다.

## 인덱스 만든다 != 항상 탄다

이거 몰랐는데 중요했다. 인덱스를 걸어놨다고 DB가 항상 그걸 쓰는 게 아니다.

DB 옵티마이저가 "이 쿼리는 인덱스 타는 게 쌀까, 그냥 풀스캔이 쌀까"를 매번 비용 추정해서 더 싼 쪽을 알아서 고른다.

대표적으로 데이터가 적을 때. 예를 들어 10건짜리 테이블이면 인덱스 안 타고 풀스캔 하는 게 낫다. 인덱스를 타면 "색인에서 위치 찾고 -> 실제 테이블 행으로 점프(랜덤 접근)"인데, 10건이면 통째로 한 페이지에 들어가니까 그냥 순차로 쭉 읽는 게 더 싸다.

그래서 인덱스 걸었으면 진짜 타는지 `EXPLAIN`으로 눈으로 확인해야 한다.

## 선택도 / 카디널리티

인덱스는 콕 집어낼 때만 이득이다. 100만 건에서 `성별='남'` 조회하면 결과가 50만 건(절반)인데, 이러면 인덱스 타봤자 50만 번 점프하느니 풀스캔이 낫다. 그래서 옵티마이저가 인덱스 무시함.

- 선택도(selectivity): 조건 하나가 전체에서 얼마나 적은 비율을 걸러내는가.
- 인덱스는 결과가 전체의 작은 비율(대략 10% 이하)일 때만 이득.
- 값 종류가 많으면(고카디널리티) 조건 하나가 적은 행만 매칭 -> 선택도 좋음 -> 인덱스 굿. `성별`은 값 2개(저카디널리티)라 꽝.

재밌는 건 이번 ES의 `src_port`. 거기선 카디널리티 높은 게 독이었다(포트마다 문서 쪼개져서 폭증). 근데 인덱스에선 고카디널리티가 약이다. 같은 성질인데 묶는 키로 쓰면 폭발, 검색 조건으로 쓰면 선택도 좋음. 맥락 따라 정반대라는 게 재밌었다.

## 복합 인덱스는 순서가 중요하다

`(이름, 나이)` 로 묶은 복합 인덱스는 전화번호부처럼 이름 먼저, 같은 이름이면 나이순으로 정렬돼 있다. 그래서 leftmost prefix(선행 컬럼) 규칙이 있다.

```sql
WHERE 이름='홍길동' AND 나이=20   -- 탐
WHERE 이름='홍길동'               -- 탐 (선행 컬럼이라 OK)
WHERE 나이=20                     -- 못 탐 (이름순 정렬이라 나이만으론 다 뒤져야 함)
```

그래서 복합 인덱스 설계할 때 자주 쓰는/등호 조건 컬럼을 앞에 둬야 한다.

## 인덱스 걸어놨는데 안 타는 실수들

원리는 하나다. 인덱스는 원본 값이 정렬된 색인인데, 그 정렬을 못 쓰게 만들면 무력화된다.

1. 컬럼에 함수/연산 씌우기

```sql
WHERE YEAR(created_at) = 2024       -- 못 탐 (가공된 값을 찾음)
WHERE created_at >= '2024-01-01'
  AND created_at <  '2025-01-01'    -- 탐 (원본 값 범위로)
```

색인은 `created_at` 원본으로 정렬돼 있는데 `YEAR(...)`로 가공한 값을 찾으니 못 씀. 컬럼은 건드리지 말고 조건 쪽을 바꿔야 한다.

2. 앞에 와일드카드 붙은 LIKE

```sql
WHERE name LIKE '김%'    -- 탐 (앞이 정해짐)
WHERE name LIKE '%김'    -- 못 탐 (끝만 아는 건 다 뒤져야 함)
WHERE name LIKE '%김%'   -- 못 탐
```

3. 형변환(암묵적 캐스팅)

```sql
-- phone 컬럼이 VARCHAR인데
WHERE phone = 01012345678    -- 숫자로 비교 -> 형변환 일어나며 무력화
WHERE phone = '01012345678'  -- 문자열로 정확히 -> 탐
```

4. `OR`, `!=`, `NOT IN` 은 "적은 걸 콕 집기"의 반대라 대체로 못 탐. `OR`은 한쪽만 인덱스 없어도 통째로 풀스캔 될 수 있다.

## 정리하면서 든 생각

- 조회 느릴 때 쿼리만 붙잡지 말고, 읽어야 할 양 자체를 줄이는 걸 먼저 봐야 한다. ES 롤업이랑 완전히 같은 결.
- 인덱스는 공짜가 아니다. 조회는 빨라지지만 INSERT/UPDATE마다 인덱스도 갱신해야 하고 용량도 든다. 그래서 아무 컬럼에나 막 걸면 안 되고, 선택도 좋은 컬럼에 필요한 만큼만.
- 다음엔 실제로 PostgreSQL에 테이블 만들어서 `EXPLAIN ANALYZE`로 인덱스 있을 때 없을 때 직접 재보기.
