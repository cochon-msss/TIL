# NAT

[DNS](dns.md) 노트에서 공유기가 NAT를 겸임한다고만 쓰고 넘어갔다. 사설 IP는 인터넷에서 못 쓰는 주소라는데, 그 주소를 쓰는 내 맥에서 구글이 어떻게 되는지가 궁금해서 봤다.

## 사설 IP는 인터넷에서 주소가 아니다

`192.168.0.x` 같은 사설 IP는 전 세계 집집마다 똑같이 쓴다. 그래서 인터넷 라우터는 이 대역이 목적지인 패킷을 버린다.

내 맥(`192.168.0.10`)이 구글에 요청을 그대로 보낸다고 하면 가는 건 문제가 없다. 목적지가 구글의 공인 IP니까. 문제는 돌아오는 길이다. 구글이 답장을 `192.168.0.10` 으로 보내야 하는데 그 주소는 인터넷에서 갈 곳이 없다.

## 공유기가 출발지를 바꿔 쓴다

공유기는 통신사한테 받은 공인 IP 하나를 갖고 있다. 패킷이 밖으로 나갈 때 출발지를 자기 공인 IP로 바꾸고, 바꾼 내역을 표에 적어둔다. 이게 NAT(Network Address Translation)다.

```
[내 맥]                    [공유기]                      [구글]
192.168.0.10:51001  ──▶  출발지를 바꿔 씀  ──▶  142.250.199.206:443
                         203.0.113.5:40001

NAT 테이블
  안쪽                     바깥쪽
  192.168.0.10:51001  ↔   203.0.113.5:40001
```

구글 입장에서는 `203.0.113.5:40001` 이 요청한 걸로 보이고 답장도 거기로 보낸다. 공유기는 답장을 받으면 표에서 `40001` 을 찾아 목적지를 `192.168.0.10:51001` 로 되돌려서 내 맥에 넘긴다.

확인은 두 개를 비교하면 된다. 값이 다르면 그 사이에서 누가 출발지를 바꿔 쓴 거다.

```
ipconfig getifaddr en0     # 내 맥이 아는 내 IP (사설)
curl ifconfig.me           # 바깥 서버가 본 내 IP (공인)
```

## IP만이 아니라 포트도 바꾼다

집에 맥이랑 폰이 같이 있으면 둘 다 공인 IP는 하나다. 답장이 왔을 때 누구 건지는 포트로 구분한다.

```
  안쪽                     바깥쪽
  192.168.0.10:51001  ↔   203.0.113.5:40001   ← 맥
  192.168.0.11:51001  ↔   203.0.113.5:40002   ← 폰 (출발지 포트가 우연히 같아도 됨)
```

[IP / 서브넷 / 포트](ip-subnet-port.md) 노트의 "연결은 4개 조합으로 구분된다"가 그대로 쓰인다. 공유기가 바깥쪽 포트를 안 겹치게 골라주니까 공인 IP 하나로 여러 대가 동시에 나갈 수 있다.

이렇게 포트까지 바꾸는 방식을 PAT(또는 NAPT)라고 한다. 집 공유기가 하는 NAT가 이거다.

## 밖에서 먼저 들어오면 버려진다

내 서버가 `192.168.0.20:8080` 을 열어두고 있을 때 밖에서 `203.0.113.5:8080` 으로 접속하면 어떻게 되나. 처음엔 8080이 열려 있으니 서버가 응답할 줄 알았는데 아니다. 서버까지 가지도 못하고 공유기에서 버려진다.

`203.0.113.5` 는 내 서버 주소가 아니라 공유기 주소다. 패킷은 일단 공유기에 도착하고, 공유기는 안쪽 누구한테 넘길지 표에서 찾는다.

```
도착한 패킷: 목적지 203.0.113.5:8080

NAT 테이블
  안쪽                     바깥쪽
  192.168.0.10:51001  ↔   203.0.113.5:40001
  192.168.0.11:51001  ↔   203.0.113.5:40002

  8080 → 없음 → 버림
```

표의 줄은 안에서 밖으로 나갈 때만 생긴다. 아무도 `8080` 으로 나간 적이 없으니 줄이 없다. "8080이 열려 있다"는 건 서버만 아는 사실이고 공유기는 모른다.

공인 IP가 아파트 건물 주소고 사설 IP가 호수라고 보면 된다. 편지에 건물 주소만 있고 호수가 없으면 경비실은 전달을 못 한다. 내가 먼저 보낸 편지의 답장만 경비실이 적어둔 기록을 보고 전달해준다.

## 포트포워딩은 표에 미리 적어두는 줄이다

밖에서 먼저 들어오게 하려면 공유기에 줄을 손으로 미리 적어둔다. 이게 포트포워딩이다.

```
NAT 테이블
  안쪽                     바깥쪽                 종류
  192.168.0.10:51001  ↔   203.0.113.5:40001     자동
  192.168.0.11:51001  ↔   203.0.113.5:40002     자동
  192.168.0.20:8080   ↔   203.0.113.5:8080      고정 (포트포워딩)
```

- 자동 줄: 안에서 패킷이 나가는 순간 공유기가 적는다. 연결이 끝나거나 한동안 조용하면 지운다
- 고정 줄: 사람이 공유기 설정 화면에서 적는다. 직접 지울 때까지 남는다

패킷이 도착했을 때 공유기가 하는 일은 둘 다 같다. 표에서 줄을 찾아 주소를 바꿔 쓰고 안쪽으로 넘긴다.

실제 장비에서는 저장 위치가 다르다. 고정 줄은 규칙으로 설정에 저장되고 자동 줄은 현재 연결 목록으로 메모리에 있다. 그래서 공유기를 껐다 켜면 자동 줄은 다 사라지는데 포트포워딩은 남는다.

## SNAT / DNAT

방향에 따라 바꾸는 게 다르고 이름도 다르다.

| | 바꾸는 것 | 줄이 생기는 시점 | 이름 |
|---|---|---|---|
| 안 → 밖 | 출발지 | 나갈 때 자동 | SNAT (집에서는 PAT) |
| 밖 → 안 | 목적지 | 사람이 미리 설정 | DNAT (포트포워딩) |

## 의도 안 했는데 방화벽처럼 동작한다

밖에서 먼저 들어오는 건 기본으로 다 버려지니까 NAT는 내부를 가려준다. [사설망](private-network.md) 노트에 적은 "외부 인터넷의 접근으로부터 내부 네트워크를 보호"가 실제로는 이 동작이다.

## 공유기에만 있는 게 아니다

NAT는 장비 이름이 아니라 기능이다. 주소 체계가 다른 두 망의 경계면 어디든 들어간다. 집에서는 그 경계가 공유기일 뿐이다.

| 위치 | 하는 일 |
|---|---|
| 집 공유기 | 사설 IP 여러 대를 공인 IP 하나로 내보냄 |
| 회사 방화벽/라우터 | 같은 일을 더 큰 규모로. 방화벽 장비가 NAT를 겸하는 경우가 많다 |
| 통신사 (CGNAT) | 공인 IP가 부족해서 가입자 여러 명을 공인 IP 하나로 묶음 |
| 클라우드 NAT Gateway | 프라이빗 서브넷의 서버가 인터넷으로 나갈 때 |
| 내 컴퓨터 안 (Docker, VM) | 컨테이너 내부 IP를 호스트 IP로 바꿈 |
| 폰 핫스팟 | 폰이 공유기 역할 |

Docker가 제일 와닿는다.

```
docker run -p 8080:80 nginx
```

`-p 8080:80` 이 포트포워딩이다. 컨테이너는 `172.17.0.2` 같은 자기만의 사설 IP를 갖고 있고 호스트가 공유기 역할을 한다.

```
호스트:8080  →  172.17.0.2:80     ← 위에서 본 고정 줄 (DNAT)
```

반대로 컨테이너가 밖으로 나갈 때는 출발지가 호스트 IP로 바뀐다(SNAT). 공유기에서 본 구조가 컴퓨터 한 대 안에서 그대로 반복된다.

## NAT는 겹친다

경계마다 NAT가 있으니 패킷 하나가 여러 번 바뀌어 나가기도 한다.

```
컨테이너 172.17.0.2
   ↓ NAT (Docker)
내 맥 192.168.0.10
   ↓ NAT (공유기)
공유기 100.64.3.7        ← 통신사가 준 주소인데 이것도 사설인 경우
   ↓ NAT (통신사 CGNAT)
공인 IP 203.0.113.5
```

통신사 CGNAT 뒤에 있으면 공유기에 포트포워딩을 걸어도 밖에서 못 들어온다. 공유기 위에 내가 설정할 수 없는 NAT가 한 겹 더 있어서다.

공유기 관리 페이지의 WAN IP랑 `curl ifconfig.me` 결과를 비교하면 알 수 있다. 둘이 다르면 위에 NAT가 더 있는 거다.

## 인터넷을 사이에 둔 사설망끼리는 먼저 접속할 방법이 없다

본사 서버(`10.0.0.5`)와 지사 PC(`192.168.1.30`)가 각각 다른 공유기 뒤에 있고 그 사이가 인터넷이라고 하자.

```
[지사]                                              [본사]
PC 192.168.1.30 ── 공유기 ══ 인터넷 ══ 공유기 ── 서버 10.0.0.5
                 198.51.100.7        203.0.113.5
```

지사 PC가 해볼 수 있는 건 두 가지인데 둘 다 실패한다.

- 서버의 사설 IP `10.0.0.5` 로 보낸다 → 인터넷 라우터가 버린다. 사설 IP는 인터넷에서 주소가 아니다
- 본사 공유기의 공인 IP `203.0.113.5:8080` 으로 보낸다 → 공유기까지는 간다. 근데 표에 `8080` 줄이 없어서 버린다

서버 주소로는 인터넷을 못 건너고, 건널 수 있는 주소로는 공유기에서 막힌다. 위에서 본 "밖에서 먼저 들어오면 버려진다"랑 같은 얘기다. 본사 공유기 입장에서는 지사도 그냥 밖이다.

같은 공유기 아래에 있으면 이런 일이 없다. 같은 사설망이라 사설 IP로 바로 통신한다. 문제가 생기는 건 서로 다른 공유기 뒤에 있고 그 사이에 인터넷이 있을 때다.

## 구글은 되는데 본사 서버는 안 되는 이유

그럼 구글은 왜 그냥 되나. 내 공유기에 포워딩을 건 적이 없는데.

포트포워딩은 받는 쪽이 거는 거다. 구글에 접속할 때 나는 보내는 쪽이라 나가는 순간 자동 줄이 생긴다. 내 쪽은 설정할 게 없다.

구글 쪽은 열어뒀다. 누구나 접속하라고 만든 서비스니까 입구에 공인 IP를 붙이고 `443` 을 열어뒀다. 뒤의 실제 서버들은 사설 IP를 쓰고 입구 장비(로드밸런서)가 요청을 안쪽으로 넘긴다. 포트포워딩이랑 같은 원리다.

```
나 ══ 인터넷 ══ [구글 입구: 공인 IP:443, 열려 있음] ── 안쪽 서버들 (사설 IP)
```

그러니까 본사, 지사만의 특별한 문제가 아니다. 규칙은 하나다. 밖에서 먼저 접속하려면 받는 쪽이 문을 열어둬야 한다. 구글이랑 본사 서버의 차이는 기술이 아니라 의도다.

| | 구글 | 본사 내부 서버 |
|---|---|---|
| 누구한테 열고 싶나 | 전 세계 누구나 | 우리 직원만 |
| 그래서 | 공인 IP로 문을 열어둠 | 문을 안 열어둠 |
| 밖에서 접속하면 | 된다 | 안 된다 |

본사 서버가 밖에서 안 되는 건 고장이 아니라 일부러 안 열어둔 결과다. NAT가 막는다기보다 NAT 뒤에 있으면 기본이 닫힌 상태인 거다.

그래서 진짜 질문은 이거다. 전 세계에는 닫아두고 지사한테만 열어주려면 어떻게 하나.

## 포트포워딩으로 열면 누구한테나 열린다

본사 공유기에 포트포워딩을 걸면 접속은 된다.

```
203.0.113.5:8080  →  10.0.0.5:8080
```

서버 한 대에 포트 하나면 이걸로 충분하다. 근데 내부 서버를 여는 용도로는 곤란한 게 많다.

- 전 세계에 열린다. 고정 줄은 지사만 통과시키는 게 아니라 그 주소로 오는 누구든 통과시킨다. 출발지 IP로 막는 방화벽 규칙을 따로 걸어야 하는데, 재택근무처럼 IP가 바뀌는 사람은 그것도 안 된다
- 암호화가 없다
- 서버, 포트마다 줄이 필요하다. 서버가 50대면 규칙이 수백 줄이다
- 포트가 겹친다. 서버 두 대가 둘 다 `8080` 을 쓰면 바깥쪽을 `8080`, `8081` 로 나눠야 하고 뭐가 뭔지 따로 외워야 한다
- 사설 IP를 못 쓴다. 본사 안에서 쓰는 주소랑 지사에서 쓰는 주소가 달라진다

포트포워딩은 서비스 하나를 밖에 공개할 때 맞는 도구다. 웹사이트를 외부에 서비스하는 경우가 그렇다.

## VPN은 패킷을 패킷 안에 넣는다

믿을 수 있는 상대한테만 내부망을 열어주는 게 VPN이다. [VPN](vpn.md) 노트에 "NAT와 같은 제약 없이 사설 IP를 이용해 통신"이라고 적었는데 그 제약이 위 상황이다. VPN은 사설 IP가 적힌 패킷을 통째로 다른 패킷 안에 넣어서 보낸다.

```
바깥 패킷:  198.51.100.7  →  203.0.113.5      ← 공인 IP끼리라 인터넷 통과
  └ 안쪽 패킷(암호화):  192.168.1.30  →  10.0.0.5:8080
```

인터넷 라우터는 바깥 주소만 보니까 그냥 전달한다. 본사 VPN 장비가 받아서 겉을 벗기면 원래 패킷이 나오고, 그걸 본사 내부망에 흘려보낸다. 이게 캡슐화고 터널링이다.

| | 포트포워딩 | VPN |
|---|---|---|
| 접속 주소 | 공인 IP + 나눠 쓴 포트 | 사설 IP 그대로 |
| 설정 단위 | 서버, 포트마다 한 줄 | 망과 망을 한 번 연결 |
| 노출 범위 | 인터넷 전체 | 터널 양 끝만 |
| 암호화 | 없음 | 있음 |

조건이 하나 있다. 두 사설망의 대역이 겹치면 안 된다. 본사랑 지사가 둘 다 `192.168.0.0/24` 를 쓰면 지사 PC는 `192.168.0.5` 가 옆자리인지 본사 서버인지 구분을 못 한다.

## 전용회선으로 이어진 사설망은 NAT도 VPN도 필요 없다

그런데 회사에서는 사업소 PC가 본사 서버에 사설 IP로 바로 붙는다. PC에 VPN을 설정한 적도 없다. 왜 되는지 봤다.

처음엔 물리적으로 떨어져 있으니 인터넷으로 이어져 있고 공인 IP를 쓸 거라고 생각했다. 멀면 인터넷으로 연결해야 한다는 전제가 틀렸다. 전용회선은 통신사에서 두 지점만 잇는 선을 통째로 빌린 거다. 양 끝에 회사 라우터만 붙어 있고 인터넷에는 연결돼 있지 않다. 사무실 랜선이 수십 km로 길어진 셈이다.

사설 IP는 멀리 못 가는 주소가 아니다. 인터넷이 그 주소가 어디 있는지 모르는 것뿐이다. 사설 IP 패킷을 버리는 건 인터넷 라우터고, 회사 내부 라우터는 안 버린다. 그 주소를 나눠준 게 회사니까 어디 있는지 안다.

회사 내선번호랑 같다. 밖에서 휴대폰으로 내선번호를 누르면 안 걸리는데, 본사와 사업소가 회사 전용 전화선으로 이어져 있으면 사업소에서 본사 내선으로 바로 걸린다.

```
인터넷을 사이에 둔 경우
  지사 ── 공유기 ══ 인터넷 ══ 공유기 ── 본사          ← 인터넷이 사설 IP를 버림

전용회선으로 이어진 경우
  사업소 10.20.122.15 ── 라우터 ══ 전용회선 ══ 라우터 ── 본사 10.20.10.175
                                                      ← 전부 회사 라우터
```

두 주소가 둘 다 `10.20.x.x` 다. 대역은 다르지만 둘 다 사설 IP다. 대역은 위치가 정하는 게 아니라 회사가 정한다. 큰 대역 하나를 잡고 사업소별로 쪼개준 구조다. 서로 다른 사설망이 아니라 여러 지역에 걸친 하나의 사설망인 거다. 회사 라우터들은 "`10.20.10.x` 는 본사 방향 회선으로 보낸다"는 경로를 알고 있어서 사설 IP 그대로 전달한다. 주소를 바꿀 일이 없으니 NAT가 없다.

[사설망](private-network.md) 노트에 적은 "주로 전용선으로 연결된 내부망"이 이 구조다.

PC 입장에서는 [IP / 서브넷 / 포트](ip-subnet-port.md) 노트의 서브넷 판단 그대로다.

1. 목적지가 나랑 같은 대역이 아니다
2. 그러면 게이트웨이(사업소 라우터)로 보낸다
3. 사업소 라우터가 경로표를 보고 본사 방향 회선으로 넘긴다
4. 본사 라우터가 목적지에 전달한다

PC에 VPN 설정이 없다고 VPN이 없다는 뜻은 아니다. 사업소 라우터와 본사 라우터끼리 터널을 맺고 있으면 PC는 아무것도 몰라도 된다.

공인 IP는 인터넷으로 나가는 출구에만 있다. 사업소에서 본사 서버로 갈 때는 전용회선만 타니까 공인 IP를 만날 일이 없고, 외부 사이트에 접속할 때만 출구를 지나면서 NAT를 거친다.

```
사업소 10.20.122.x ══ 전용회선 ══ 본사 10.20.10.x
                                     │
                                  방화벽/NAT ── 공인 IP ══ 인터넷
```

정리하면 NAT가 필요한 건 사설망과 인터넷의 경계를 넘을 때다. 사설 IP끼리의 통신은 경로([라우팅](routing.md))만 있으면 된다.

| 두 지점 사이에 있는 것 | 사설 IP로 직접 통신 | 필요한 것 |
|---|---|---|
| 같은 스위치 (같은 서브넷) | 가능 | 없음 |
| 회사 라우터와 전용회선 | 가능 | 라우팅 경로 |
| 인터넷 | 불가 | 포트포워딩 또는 VPN |
