# ARP

[라우팅](routing.md) 노트에서 내 맥 라우팅 테이블을 찍었을 때 MAC 주소가 적힌 줄들이 있었다. 그게 뭔지 봤다.

처음엔 ARP가 MAC을 IP로 바꾸고 RARP가 IP를 MAC으로 바꾸는 줄 알았는데 반대다.

- ARP: IP → MAC. "이 IP 쓰는 기기, MAC 주소가 뭐야?"
- RARP: MAC → IP. "내 MAC이 이건데 내 IP가 뭐야?"

## 왜 IP → MAC 방향이냐

라우팅에서 이어진다. 구글로 보낼 때 내 맥은 라우팅 테이블을 보고 "공유기 `192.168.219.1` 한테 넘긴다"까지 정한다. 근데 와이파이나 랜선 위에서 실제로 전달할 때는 IP가 아니라 MAC 주소로 받는 사람을 지정한다.

그래서 한 단계가 더 있다.

```
① 라우팅: 다음 칸은 192.168.219.1 이다        ← IP는 앎
② ARP:    192.168.219.1 의 MAC이 뭐지?        ← MAC은 모름. 물어봄
③ 전달:   그 MAC 앞으로 보낸다
```

아는 게 IP고 모르는 게 MAC이니까 ARP는 IP를 주고 MAC을 알아내는 방향이다.

## 물어보는 방법은 다 들리게 외치기다

같은 대역 전체에 방송(브로드캐스트)한다. "`192.168.219.1` 쓰는 사람?" 하면 해당 기기만 "나야, 내 MAC은 이거야" 하고 답한다.

```
내 맥  ──▶  (대역 전체에)  192.168.219.1 누구야?
공유기 ──▶  (내 맥한테만)  나야. dc:70:35:1a:bb:45
```

답을 받으면 잠깐 기억해둔다. 매번 외치면 시끄러우니까. 이 기억이 ARP 캐시고, 라우팅 테이블에 있던 MAC 줄들이 이거였다.

```
192.168.219.1      dc:70:35:1a:bb:45   ...   1169
```

끝의 숫자는 남은 기억 시간(초)이다. 지나면 지우고 필요할 때 다시 물어본다. `arp -a` 로 따로 볼 수도 있다.

같은 대역 안에서만 쓴다. 방송이 대역 밖으로는 안 나가니까. 구글 MAC은 물어볼 일이 없다. 내 맥은 다음 칸인 공유기 MAC만 알면 되고, 그다음은 공유기가 자기 다음 칸 MAC을 알아서 물어본다.

## 같은 IP를 두 대가 쓰면

IP 충돌이다. 공유기가 `192.168.219.50` 의 MAC을 물어보면 두 대가 다 "나야" 하고 답한다.

```
공유기 ──▶  192.168.219.50 누구야?
PC A   ──▶  나야. aa:aa:aa:aa:aa:aa
PC B   ──▶  나야. bb:bb:bb:bb:bb:bb
```

ARP 캐시에는 IP 하나에 MAC 하나만 적힌다. 나중에 온 답이 앞의 걸 덮어쓴다. 그래서 그 순간 마지막으로 답한 쪽으로 패킷이 간다.

처음엔 "마지막에 점유한 애가 되겠지"라고 생각했는데 대충 맞다. 다만 한 번 정해지고 끝나는 게 아니라 더 지저분하다.

- 캐시가 만료돼서 다시 물어볼 때마다 승자가 바뀔 수 있다
- 기기마다 캐시가 따로라서 공유기는 A로 보내고 프린터는 B로 보내는 식으로 갈릴 수 있다
- 연결 도중에 승자가 바뀌면 응답이 엉뚱한 기기로 가서 연결이 끊긴다

그래서 증상이 "아예 안 된다"가 아니라 "됐다 안 됐다 한다"로 나온다. 둘 다 반쯤 되는 상태라 원인 찾기가 어렵다.

OS는 이걸 잡으려고 IP를 받으면 "이 IP 내가 쓴다"고 한 번 외쳐본다. 누가 이미 쓰고 있어서 답이 오면 IP 주소 충돌 경고를 띄운다. 주로 누가 고정 IP를 손으로 넣었는데 그게 DHCP가 다른 기기한테 준 IP랑 겹칠 때 생긴다.

## 일부러 거짓말하면 공격이 된다

ARP는 답하는 쪽을 검증하지 않는다. "나야" 하면 그냥 믿는다. 그래서 같은 대역에 있는 누군가가 "`192.168.219.1`(공유기)은 나야"라고 계속 답하면, 다른 기기들이 공유기한테 보낼 패킷을 전부 그 기기로 보낸다. 이게 ARP 스푸핑이다. 중간에서 패킷을 보고 넘겨주면 피해자는 눈치를 못 챈다.

IP 충돌은 실수로 생긴 거고 ARP 스푸핑은 같은 구멍을 일부러 쓰는 거다. 같은 대역 안에 들어와야 할 수 있어서 공용 와이파이가 위험하다는 얘기가 여기서 나온다.

## RARP는 지금 거의 안 쓴다

RARP는 반대 상황이다. 하드디스크 없는 옛날 단말기는 켜질 때 자기 IP를 몰랐다. 아는 건 랜카드에 박힌 자기 MAC뿐이라 "내 MAC이 이건데 내 IP 좀 알려줘" 하고 물었다.

지금은 이 역할을 DHCP가 가져갔다. "켜졌는데 내 IP를 모른다"는 같은 문제를 예전엔 RARP로 풀었고 지금은 DHCP로 푼다는 뜻이다.

```
RARP 시절:  "내 MAC이 aa:bb:.. 인데 내 IP 뭐야?"  →  "192.168.0.10"
DHCP 지금:  "나 새로 왔는데 IP 좀 줘"            →  "192.168.0.10 써.
                                                   게이트웨이는 192.168.0.1,
                                                   DNS는 192.168.0.1,
                                                   24시간 동안 빌려줄게"
```

RARP가 밀려난 이유는 세 가지다.

- IP만 알려줬다. IP만 있으면 인터넷을 못 한다. 게이트웨이(`default` 줄)를 알아야 밖으로 나가고 DNS 서버를 알아야 이름으로 접속한다
- 관리자가 표를 손으로 다 적어야 했다. RARP 서버는 "이 MAC은 이 IP"라는 표를 들고 답해주는데, 기기가 새로 들어올 때마다 그 MAC을 알아내서 한 줄씩 추가해야 했다. 표에 없으면 IP를 못 받는다
- 같은 대역 안에서만 됐다. ARP처럼 방송으로 묻는 방식이라 라우터를 못 넘는다. 대역마다 RARP 서버를 하나씩 둬야 했다

DHCP는 이걸 다 해결했다.

| | RARP | DHCP |
|---|---|---|
| 주는 것 | IP만 | IP, 서브넷 마스크, 게이트웨이, DNS |
| IP 정하는 법 | 관리자가 MAC마다 미리 적어둠 | 남는 IP 중에서 알아서 골라줌 |
| 처음 보는 기기 | 못 받음 | 바로 받음 |
| 기간 | 없음 | 빌려주고 기한 지나면 회수 |

제일 큰 차이는 두 번째 줄이다. DHCP는 "`192.168.0.100` ~ `200` 은 나눠줄 수 있음"처럼 범위만 정해두면 새 기기가 왔을 때 비어 있는 IP를 하나 골라서 빌려준다. 카페 와이파이에 처음 붙는 내 폰도 바로 IP를 받는 이유다. 관리자가 내 폰 MAC을 미리 알 리가 없으니까.

라우팅 노트에 적은 "`default` 줄은 DHCP가 알려준다"도 이거고, 위에 적은 IP 충돌도 여기서 나온다. DHCP는 자기가 빌려준 IP만 알고 누가 손으로 넣은 고정 IP는 모른다. 그래서 그 IP를 다른 기기한테 또 빌려줄 수 있다.

| | 아는 것 | 묻는 것 | 지금 |
|---|---|---|---|
| ARP | 상대 IP | 상대 MAC | 매 순간 쓰임 |
| RARP | 내 MAC | 내 IP | 거의 안 씀. DHCP로 대체 |

ARP가 기본이고 기본은 IP로 MAC 찾기다. R(Reverse)이 붙으면 그 반대다.
