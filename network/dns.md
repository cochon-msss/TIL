# DNS

사내 서버는 IP를 직접 쳐서 접속하는데 구글은 `google.com`이라고 친다. 둘 다 결국 IP로 가는데 왜 다른지가 궁금해서 봤다.

## 사람과 컴퓨터가 쓰는 게 다르다

컴퓨터는 IP 주소로만 통신한다. 이름 같은 건 모른다. 반대로 사람은 `142.250.199.206` 같은 걸 못 외운다. 그 사이를 번역해주는 게 DNS다.

```
나:   google.com 접속              ← 사람이 쓰는 이름
      ↓
     [ DNS ]                       ← 번역
      ↓
     142.250.199.206 로 TCP 연결    ← 컴퓨터가 쓰는 주소
```

주소창에 이름을 치면 브라우저가 요청을 보내기 전에 먼저 DNS에 물어본다. IP를 받은 다음에야 그 IP로 TCP 연결을 맺는다. 작고 빠른 질문 하나라 UDP 53번을 쓴다.

## 공유기가 DNS 서버이기도 하다

내 맥이 어디에 물어보는지 찍어보면 (`scutil --dns`, `route -n get default`) 이렇게 나온다.

```
게이트웨이      : 192.168.0.1
DNS 서버 목록   : 2001:270::3:1     ← 통신사 DNS
                 192.168.0.1       ← 공유기. 게이트웨이와 같은 주소
```

게이트웨이랑 DNS 주소가 같다. 집 공유기는 작은 기계 하나가 라우터, DHCP, DNS, NAT, 방화벽을 다 겸임하기 때문이다. 역할이 같은 게 아니라 한 기계가 둘 다 하고 있는 거다.

- 게이트웨이 = 밖으로 나가는 출구. "이 패킷 어디로 보내?"
- DNS = 이름 번역. "이 이름 번지수가 뭐야?"

그리고 공유기가 번역표를 들고 있는 게 아니다. 그 작은 기계에 전 세계 도메인이 들어갈 수가 없다. 하는 일은 대신 물어봐주고(포워더) 알아낸 걸 적어두는 것(캐시)뿐이다. 그 증거가 위 목록이다. 공유기만 있으면 될 텐데 통신사 DNS가 같이 등록돼 있다. 모를 때 갈 곳이 필요하니까.

## 왜 번역표를 한 곳에 안 모았냐

제일 단순하게 생각하면 전 세계 도메인을 한 서버에 다 모아두고 거기 물어보면 된다. 실제로 그렇게 안 한다.

1. 규모 - 도메인이 수억 개고 전 세계 질의가 초당 수백만 건이다. 한 서버가 못 버틴다
2. 단일 장애점 - 그 서버 하나 죽으면 전 세계가 이름으로 접속 불가다
3. 거리 - 지구 반대편에서 매번 물어보면 느리다
4. 관리 권한 - 내가 내 도메인 IP를 바꿀 때마다 중앙에 신청해야 하면 지옥이다

그래서 계층으로 쪼개고 권한을 위임했다. 그리고 가까운 곳에 캐시를 깔았다.

## 도메인은 뒤에서부터 읽는다

```
www . google . com .
 │      │       │   └─ 루트 (보통 생략되는 마지막 점)
 │      │       └───── TLD. 최상위 구획
 │      └───────────── 이 칸을 구글이 소유
 └──────────────────── 호스트 이름
```

오른쪽이 상위고 왼쪽으로 갈수록 하위다. 폴더 경로를 거꾸로 쓴 셈이다.

`.com`이랑 `co.kr`이 비슷한 개념인데 계층 깊이가 다르다.

```
.com          gTLD. 전 세계 공통 상업용. 한 단계로 끝
.kr           ccTLD. 국가 최상위
  co.kr       그 아래를 용도별로 또 쪼갠 것 (co 상업, or 비영리, go 정부, ac 대학)
```

이렇게 쪼갠 건 관리 권한을 넘기려고다. 루트는 ICANN이, `.com`은 Verisign이, `.kr`은 KISA가 관리한다. 그래서 `.kr` 규칙은 한국에서 정한다.

## 실제 질의 과정

`dig +trace google.com` 으로 찍어보면 4단계로 내려간다.

```
① 루트에 물어봄
   .  →  NS  a.root-servers.net. ~ m.root-servers.net.  (13개)
   "난 google.com 몰라. 근데 .com 담당자는 알아"

② .com 담당자에게
   com.  →  NS  a.gtld-servers.net. ~ m.gtld-servers.net.
   "난 몰라. 근데 google.com 담당자는 알아"

③ google.com 담당자에게
   google.com.  →  NS  ns1.google.com. ~ ns4.google.com.
   (구글이 직접 운영. 여기가 권위 서버)

④ 답
   google.com.  →  A  142.250.199.206
```

핵심은 아무도 전체를 모른다는 거다. 각 단계는 "나는 모르지만 다음에 물어볼 곳은 안다"만 알려준다.

길 물어보는 거랑 같다. 서울시청에 "역삼동 몇 번지 김씨" 물으면 모른다. 강남구청 가보라고 한다. 거기도 모르고 역삼동 주민센터로 보낸다. 거기서 답이 나온다.

위임이 동작하는 모습이 이거다. 구글이 IP를 바꾸려면 ③번만 고치면 된다. 루트나 Verisign에 신청할 필요가 없다. ③번이 구글 소유니까.

루트 서버는 이름이 13개(`a`~`m`)인데 실제 물리 서버는 전 세계 수백 대다. 같은 IP를 여러 곳에서 응답하게 하는 애니캐스트 방식으로 2번 문제(단일 장애점)를 막아뒀다.

## TTL - 캐시 유효시간

`dig +trace` 출력의 중간 숫자가 TTL이다. 초 단위다.

```
.              451753  ≈ 5일    ← 루트. 거의 안 바뀜
com.           172800  = 2일    ← .com 담당 서버
google.com NS  172800  = 2일    ← 구글 네임서버 주소
google.com A      300  = 5분    ← 실제 IP. 짧다
```

상위로 갈수록 길고 실제 IP는 짧다. 루트 주소는 몇 년에 한 번 바뀌니 5일 캐시해도 되지만, 서비스 IP는 장애 나거나 트래픽 분산할 때 바로 갈아야 하니 5분만 캐시한다. 그래서 매번 루트까지 안 간다. 보통 ②③은 캐시에 있고 ④만 새로 물어본다.

실제로 `google.com`을 두 번 조회했는데 IP가 달랐다. `142.250.197.46` 에서 `142.250.199.206` 으로. 구글이 트래픽을 돌리고 있는 거고, TTL이 300초인 이유가 이거다.

## 도메인 하나에 항목이 여러 개다

도메인은 번지수 하나가 아니다. 이름표 하나에 여러 정보가 매달린 묶음이다.

명함 같은 거다. 회사 이름 하나에 전화번호, 주소, 이메일이 각각 적혀 있고 묻는 항목이 다르다. 그 항목 이름이 레코드 타입이다.

| 타입 | 묻는 것 | 답 예시 |
|---|---|---|
| `A` | 웹 서버 IPv4 | `223.130.192.247` |
| `AAAA` | 웹 서버 IPv6 | (없는 도메인도 많다) |
| `CNAME` | 이 이름의 본명 | `www.naver.com.nheos.com.` |
| `MX` | 메일 서버 | `10 mx1.mail.naver.com.` |
| `NS` | 담당 네임서버 | `ns1.naver.com.` |
| `TXT` | 아무 텍스트 | 소유권 증명 문자열 |

`naver.com`을 찍어보면 웹 서버는 `223.130.192.247` 인데 메일 서버는 `mx1.mail.naver.com` 이다. 완전히 다른 기계다. 그래서 레코드 타입이 나뉘어 있다. 메일 보낼 때는 `@` 뒤를 떼서 MX를 조회한다. A를 조회하면 웹 서버로 가버려 메일이 안 간다.

`A`는 보통 여러 개 나온다. 한 이름에 IP를 네 개쯤 걸어두고 돌려가며 답해서 부하를 나눈다.

`MX` 앞의 숫자는 우선순위고 낮은 쪽이 먼저다. `10`번에 보내고 안 되면 `20`번으로 간다. 메일은 유실되면 안 되니 백업 경로를 DNS에 박아둔 거다.

`TXT`에는 `google-site-verification=...` 같은 게 들어있다. 소유권 증명 흔적이다. 구글이 문자열을 주고 DNS에 넣어보라고 하는데, 넣을 수 있으면 DNS를 고칠 권한이 있다는 뜻이니 소유자가 증명된다. 도메인 인증이랑 스팸 방지(SPF) 다 TXT로 한다.

`CNAME`은 별명이다.

```
www.naver.com  →  www.naver.com.nheos.com.  →  223.130.200.236
                  (CNAME, 본명)                 (그 본명의 A)
```

`www`가 IP를 직접 안 갖고 본명을 알려주며 넘긴다. 실제 IP가 바뀔 때 한 군데만 고치면 되니까다. `www`, `blog`, `shop` 을 다 CNAME으로 걸어두면 IP 변경 때 하나만 바꾸면 끝인데, A로 각각 박아뒀으면 세 개를 다 고쳐야 한다.

## hosts가 DNS보다 먼저다

이름을 IP로 바꿀 때 제일 먼저 보는 건 DNS가 아니다. 로컬 파일을 먼저 본다.

`/etc/hosts` 를 열어보면 이게 들어있다.

```
127.0.0.1	localhost
```

`localhost`는 DNS에 물어본 적이 없다. 전 세계 어느 DNS 서버도 localhost가 뭐냐는 질문을 받지 않는다. 저 파일에 적혀 있어서 바로 답이 나온다.

전체 순서로 놓으면 이렇게 된다.

```
이름 입력
   │
   ├─ ① /etc/hosts 에 있나?        → 있으면 끝. DNS 안 감
   ├─ ② 내 컴퓨터 DNS 캐시          → 있으면 끝
   ├─ ③ 공유기 / 통신사 DNS 캐시     → 있으면 끝
   └─ ④ 루트 → TLD → 권위 서버      ← 아무도 모를 때만 여기까지
```

위에서 걸리면 아래로 안 간다. 그래서 ④번까지 가는 경우는 드물고 대부분 ②③에서 끝난다.

hosts는 DNS보다 우선이라 여기에 뭘 적든 그게 이긴다. 개발할 때 운영 도메인을 로컬로 돌려 테스트하거나, 광고 도메인을 `127.0.0.1` 로 보내 막는 데 쓴다.

반대로 장애 원인도 된다. DNS는 정상인데 내 PC만 접속이 안 되면 hosts에 옛날 줄이 남아있는 경우가 흔하다. 우선순위가 높아서 DNS를 아무리 고쳐도 안 바뀐다.

## 사설 IP에는 이름을 못 붙인다

처음 질문으로 돌아가면, 사내 서버에 IP를 직접 치는 이유는 그 서버에 이름이 없기 때문이다.

`192.168.x.x` 는 사설 IP다. 공인 DNS에 등록할 수가 없다. 등록해도 외부에서는 그 주소로 갈 수 없으니 의미가 없다.

그래서 보통 둘 중 하나를 한다. 사내에 DNS 서버를 하나 두고 사내용 이름을 등록하거나(공유기가 DNS 하던 거랑 같은 구조인데 사내 이름을 추가로 들고 있는 것), 각자 hosts에 한 줄 넣는 거다.

```
192.168.0.10   wiki.local
```

이러면 `wiki.local` 로 쓸 수 있다. 위 ①번 단계를 직접 쓰는 셈이다.

## 참고 - IP로 https 접속하면 인증서 경고가 뜬다

사설 IP를 생으로 쓰면 부작용이 하나 있다. 인증서 경고다.

https 인증서는 도메인 이름에 발급된다. `wiki.example.com` 용 인증서라고 적혀 있는데 IP로 접속하면, 브라우저가 증명서에 적힌 이름과 접속한 주소가 다르다고 판단해서 경고를 띄운다.

[HTTPS](https.md) 노트의 인증서 검증 단계 중 이름 일치 확인에 걸리는 거다. 암호화 자체는 되는데 "너 진짜 그 서버 맞아?"를 확인할 수 없는 상태다.

그래서 서버에 이름을 붙이는 건 편의 문제만이 아니라 인증서를 제대로 쓰기 위한 전제이기도 하다.
