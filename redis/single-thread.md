# Redis 싱글 스레드 — 명령 하나는 안 섞이지만, 여러 개는 섞인다

[Redis 메모리](redis-memory.md) 노트에 이어서.

Redis는 명령을 **스레드 하나**로 처리한다. 요청이 1000개 와도 한 줄로 세워서 하나씩 실행한다. 톰캣이 요청마다 스레드 붙여서 동시에 처리하는 것과 반대다.

```
요청들 → [ set a ][ get b ][ incr c ][ del d ] → 스레드 1개가 순서대로
```

## 왜 하나만 쓰나

처음엔 "데드락 때문"이라고 했다. 방향은 맞는데 데드락은 **락을 쓰면** 생기는 문제 중 하나다. 한 단계 앞이 있다.

여러 스레드가 같은 데이터를 건드리면 이렇게 된다.

```
조회수 = 10

스레드 A: 읽음(10) ───────── +1 → 11 저장
스레드 B:     읽음(10) ── +1 → 11 저장

결과: 11  (두 번 올렸는데)
```

막으려면 락을 걸어야 하고, 락에는 비용이 붙는다. 잡고 풀고 기다리는 비용, 잘못 걸면 데드락, 스레드 바꿔가며 실행하는 컨텍스트 스위칭.

Redis는 **스레드를 하나로 둬서 동시에 건드리는 상황 자체를 없앴다.** 그래서 락이 필요 없다.

하나씩이면 느리지 않냐 — 명령 하나가 메모리 안에서 마이크로초 단위로 끝난다. 느린 건 네트워크 왕복이지 실행이 아니다. 스레드 늘려봐야 별로 안 빨라진다.

## INCR — 명령 하나로 읽고 올리고 쓴다

`INCR` 은 숫자를 1 올리는 Redis 명령이다(increment). 자바에선 `opsForValue().increment("조회수")`.

```
redis-cli> SET 조회수 10
redis-cli> INCR 조회수    → 11
```

이게 Redis 안에서 **읽기 → +1 → 저장**을 한 번에 한다. 서버 두 대가 동시에 `INCR` 보내면 12가 된다. 차례로 하나씩 실행되니까. 중간에 끼어들 틈이 없는 걸 **원자적(atomic)**이라고 한다. 같은 계열로 `DECR`(-1), `INCRBY key 5`(+5).

## 근데 싱글 스레드인데 또 11이 나온다

예전 코드 방식대로 조회수를 올리면 이렇다.

```java
String v = getSingleData("조회수");              // ① GET
setSingleData("조회수", Integer.parseInt(v) + 1); // ② SET
```

```
서버 A:  GET(10) ──────────── SET 11
서버 B:       GET(10) ── SET 11

결과: 11
```

흐름은 이해했는데 **"이게 말이 되나? 싱글 스레드라며"** 싶었다. 이게 핵심이었다.

Redis가 받은 명령 순서를 보면 진짜로 하나씩 처리했다.

```
Redis 줄:  [GET ←A] [GET ←B] [SET 11 ←B] [SET 11 ←A]
```

문제는 **+1을 Redis가 아니라 자바가 했다**는 거다.

```
GET → (네트워크) → 자바에서 +1 → (네트워크) → SET
       └────── 이 틈에 다른 서버 명령이 끼어듦 ──────┘
```

이 틈은 Redis 바깥이라 싱글 스레드가 못 지켜준다.

> 싱글 스레드가 보장하는 건 **명령 하나**가 안 섞인다는 것. **명령 여러 개 조합**은 안 지켜준다.

## 재고는 반대로 너무 많이 줄어든다

"재고가 0보다 크면 1 줄인다"를 GET으로 확인 → DECR로 줄이면? 재고 1개 남았을 때 서버 두 대가 동시에.

"안 줄어들겠는데"라고 했는데 반대였다. **너무 많이 줄어든다.**

```
재고 = 1

서버 A:  GET → 1 (OK) ────────── DECR → 0
서버 B:      GET → 1 (OK) ── DECR → -1

결과: -1   (1개를 두 명이 삼)
```

| | 흐름 | 결과 |
|---|---|---|
| 조회수 | GET → 자바 +1 → **SET** | 덮어써서 한 번 사라짐 → 11 |
| 재고 | GET → 자바 확인 → **DECR** | DECR은 각자 원자적이라 둘 다 반영 → -1 |

DECR 자체는 멀쩡히 두 번 실행됐다. **"0보다 크다"는 확인이 이미 낡은 정보**였다. 선착순 쿠폰, 재고에서 나는 초과 판매가 이거다.

## Lua 스크립트 — 판단까지 Redis 안으로

Lua는 작은 프로그래밍 언어고, Redis 안에 Lua 실행 기능이 있다. 명령 여러 개 + if 같은 로직을 **통째로 Redis에 보내서 Redis 안에서** 돌린다.

```lua
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock > 0 then
  return redis.call('DECR', KEYS[1])
end
return -1
```

```
보통   자바 → GET → 자바가 판단 (← 여기 틈) → DECR
Lua    자바 → [GET, if, DECR] 통째로 → Redis가 안에서 다 실행 → 결과만 받음
```

Redis는 스크립트 전체를 **명령 하나처럼** 취급한다. 실행 중에 B의 명령이 오면 스크립트 끝날 때까지 줄에서 기다린다. 그래서 B는 재고 0을 보고 품절 처리된다.

```
싱글 스레드       → 명령 하나는 안 섞인다
명령 여러 개      → 사이에 틈이 생긴다 (GET-SET, GET-DECR)
INCR / Lua       → 틈을 Redis 안으로 넣어서 없앤다
```

## 그 대신 — 느린 명령 하나가 전부를 막는다

"B가 기다린다"가 단점이 될 때가 있다. Lua 안에 키 100만 개 도는 반복문 넣어서 5초 걸리면? 다 기다린다 ㅋㅋ 그 Redis 쓰는 모든 서버의 로그인, 캐시, 재고 확인이 5초 멈춘다. 그래서 Lua는 짧게 쓴다.

같은 이유로 운영에서 `KEYS *` 쓰지 말라고 한다. 키 수백만 개면 이것도 몇 초 멈춘다. 대신 `SCAN` 을 쓴다.

```
KEYS *    한 번에 전부 → 그동안 모두 대기
SCAN 0    조금 → 다른 명령 처리 → 조금 더 → …
```

락이 필요 없다는 장점과 **하나가 느리면 전부 느리다**는 단점이 같은 동전의 양면이다.
