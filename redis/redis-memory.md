# Redis는 메모리에 둔다 — TTL, 캐시와 세션, 영속화

예전에 Spring Boot로 Redis set/get/delete 해본 [코드](https://github.com/cochon-msss/Redis)가 있는데, 다시 보니 기억이 거의 안 났다. 이직 준비하면서 개념부터 다시 잡았다.

## 왜 굳이 Redis를 따로 띄우나

조회·저장·삭제는 MySQL 테이블 하나로도 된다. 그런데도 따로 띄우는 이유는 **데이터를 디스크가 아니라 메모리(RAM)에 두니까 빠르다**는 거다.

빠른 대신 대가가 있다.

```
              MySQL          Redis
저장 위치      디스크          메모리
속도          느림            빠름
용량          큼 (TB)         작음 (GB)
전원 꺼지면    남음            날아감 (기본은)
```

## 유효시간(TTL)을 거는 이유

예전 코드에 `duration` 있으면 `set(key, value, duration)` 으로 저장하는 부분이 있었다. 왜 거는지 생각해 보면 두 가지다.

- **용량** — 메모리는 작다. 안 쓰는 건 알아서 사라지게 한다
- **정합성** — DB 원본이 바뀌어도 Redis엔 옛날 값이 남는다. 시간 지나면 지우고 다시 가져온다

처음엔 "만료되면 서버를 다시 조회한다"고 했는데 정확히는 **DB를 다시 조회**한다.

```
조회 요청 → Redis에 있나?
             ├ 있음 → 바로 응답 (빠름)
             └ 없음(만료됨) → DB 조회 → Redis에 다시 set(유효시간) → 응답
```

이렇게 DB 앞에 두는 걸 **캐시**라고 한다.

## 세션도 TTL을 거는데, 이유가 다르다

[프록시](../network/proxy.md) 노트에서 톰캣이 여러 대면 세션을 Redis로 빼낸다고 했었다. 세션에도 유효시간을 건다.

"세션 원본은 어디 있냐"는 질문에 **서버에 있다**고 답했는데 틀렸다. 톰캣 메모리에서 꺼내서 Redis로 **옮긴** 거라, 옮기고 나면 **Redis에만** 있다. 다른 사본이 없다.

| | 캐시 | 세션 |
|---|---|---|
| Redis 속 값 | DB의 사본 | 그게 유일한 원본 |
| 만료되면 | DB에서 다시 가져오면 됨 | 되살릴 데가 없음 → 로그아웃 |
| 유효시간의 의미 | "이 사본 너무 오래됐다" | "이 로그인 이제 끝" |

똑같이 `set(key, value, duration)` 인데 성격이 다르다. 캐시는 만료돼도 손해가 없고, 세션은 **만료되는 것 자체가 목적**이다. 30분 아무것도 안 하면 로그아웃.

## Redis가 재시작되면

메모리가 날아간다. 이것도 처음엔 둘 다 "다시 채워지겠지"라고 똑같이 답했다.

- 캐시 — 맞다. DB에서 다시 채운다. 처음 몇 번만 좀 느리다
- 세션 — "새 세션이 생긴다"는 맞는데, 그건 **로그인 안 된 빈 세션**이다

```
재시작 전   session:abc → { userId: 7, 로그인됨 }
재시작 후   session:abc → (없음)

다음 요청 → 세션 없음 → 빈 세션 발급 → 로그인 페이지로
```

**접속해 있던 사용자 전원이 한꺼번에 로그아웃된다.** 위 표 차이가 실제로 터지는 장면이 이거다.

## 재시작해도 안 날아가게 — RDB / AOF

이게 되나 싶었는데 된다. 메모리에 있는 걸 **디스크에도 적어두고**, 재시작할 때 다시 읽어 들인다.

```
RDB   일정 시간마다 메모리 전체를 통째로 파일로 저장 (스크린샷)
AOF   쓰기 명령(set, del …)을 하나하나 파일에 이어 적음 (키 입력 기록)
```

"Redis = 꺼지면 날아간다"는 **기본 성질**이지 고정이 아니다. 속도는 메모리에서 내고, 디스크는 재시작 대비 보험이다.

### RDB의 빈틈

5분마다 찍는데 찍고 3분 뒤에 죽으면? 3분 전 사진으로 돌아간다. **그 3분 사이에 로그인한 사람만** 로그아웃된다.

그 빈틈 메우려고 AOF가 있는데, AOF도 적었다고 바로 디스크에 박히는 게 아니다. OS가 모아뒀다가 내보내서, 얼마나 자주 강제로 내보낼지 고른다.

```
always     명령마다 확정       거의 안 잃음, 느림
everysec   1초마다 (기본값)    최대 1초 잃음, 빠름
no         OS한테 맡김         더 빠름, 수십 초 잃을 수도
```

"얼마나 안 잃을까"와 "얼마나 빠를까"의 맞바꿈이다. Redis 쓰는 이유가 속도니까 보통 everysec.

### 캐시만 담는 Redis면?

영속화 안 켜도 된다. 여기서 이유를 **"유효시간이 있으니까"**라고 했는데 틀렸다. 그러면 세션도 유효시간이 있으니 저장 안 해도 된다는 말이 된다.

진짜 이유는 **원본이 DB에 따로 있으니까**다. 날아가도 다시 채우면 된다.

예외로, 캐시가 엄청 큰 서비스는 일부러 RDB를 켜기도 한다. 재시작으로 캐시가 텅 비면 요청이 전부 DB로 몰리니까. 데이터를 지키려는 게 아니라 **DB를 보호하려는** 거다.

## 덤: 직렬화

예전 코드 `RedisConfig` 에 `StringRedisSerializer` 를 설정해 뒀었다. Redis는 자바 객체를 모르고 **바이트 덩어리**만 받는다. 아무것도 설정 안 하면 `RedisTemplate` 이 자바 기본 직렬화를 써서 키에 자바 전용 머리말이 붙는다.

```
set("hello", "world")

기본 직렬화     redis-cli> keys *   →  "\xac\xed\x00\x05t\x00\x05hello"
String 직렬화   redis-cli> keys *   →  "hello"
```

기본으로 두면 `redis-cli` 에서 `get hello` 해도 못 찾고, 다른 언어 서버도 못 읽는다.
